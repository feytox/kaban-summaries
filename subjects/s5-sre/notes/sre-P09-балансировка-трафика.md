# P09. Балансировка трафика

Итог семинара: надёжность начинается с нескольких копий, а балансировка делает их полезными. ([01:12:44](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=4364))

## Избыточность работает при независимых копиях

Одна копия приложения - единая точка отказа. Несколько одинаковых копий за балансировщиком переживают отказ одной: балансировщик перестаёт слать ей новые запросы. ([02:24](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=144))

Если одна копия отказывает с вероятностью 1%, то три независимые откажут разом с вероятностью 0,0001%. Расчёт верен при двух условиях: ([03:17](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=197))
- отказы независимы: общая база или один дата-центр роняют все копии сразу, поэтому копии ещё и геораспределяют;
- оставшимся копиям хватает мощности, иначе они перегрузятся и начнут отключаться по очереди.

Каждая копия дорога в развёртывании, сопровождении и диагностике, поэтому избыточность проектируют для критичных частей. Как снижать эту стоимость: [?] в записи неразборчиво, что-то про меньший ручной труд. ([04:50](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=290))

## Балансировщик выбирает доступный экземпляр

Балансировщик не просто раскидывает запросы: он исключает недоступные экземпляры, а иногда расшифровывает HTTPS, ограничивает и повторяет запросы. Его самого тоже резервируют. ([05:31](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=331))

**Активная проверка** - балансировщик сам периодически опрашивает `/ready` или TCP-подключение. ([06:21](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=381))

**Пассивная проверка** - балансировщик анализирует ответы на реальные запросы: ошибки и таймауты. Она ловит сервер, который отвечает на health-эндпоинт, но падает на оформлении заказа, зато дороже по ресурсам. Обычно обе проверки работают вместе. ([08:00](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=480))

| Алгоритм          | Как выбирает                                  |
| ----------------- | --------------------------------------------- |
| Round robin       | по кругу: A, B, C, A                          |
| Взвешенный        | A: 80, B: 20 - доля, а не точный процент      |
| Least connections | экземпляр с наименьшим числом соединений      |
| Sticky sessions   | все запросы пользователя - на одну копию      |

([13:06](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=786))

- Веса сходятся к заданной доле на тысячах запросов, на сотне возможно 60/40.

Sticky sessions нужны приложению с локальным состоянием: сессией, кешем, матчем онлайн-игры. Цена - зависимость от копии: упала копия - потеряно состояние, а тяжёлый пользователь тормозит всех приклеенных к его копии. Таких "шумных соседей" отслеживают и переносят. ([15:05](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=905), [16:40](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1000))

## L4 делит соединения, L7 - запросы

**L4-балансировка** видит IP, порт и TCP/UDP-соединение, не HTTP. Сервер выбирается при установке соединения, поэтому 100 запросов клиента по одному keep-alive соединению попадут в один под при простаивающих остальных. ([09:57](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=597))

**L7-балансировка** понимает HTTP: путь, заголовки, метод. L7-прокси вроде Envoy разбирает отдельные запросы внутри соединения, в том числе потоки HTTP/2 и gRPC, и раскидывает их по разным подам. ([12:12](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=732))

## Без балансировщика

Очередь подходит, когда результат не нужен сразу: отчёт, письмо. Свободные воркеры забирают задания параллельно, пики нагрузки сглаживаются. Очередь может доставить сообщение повторно, поэтому обработчики делают идемпотентными, особенно списание денег. ([18:25](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1105), [21:00](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1260))

**Клиентская балансировка** - клиент сам получает список экземпляров через service discovery (DNS или API) и выбирает по своему алгоритму. Так в RPC-системах обходятся без прокси, но клиент сам обновляет список и обрабатывает отказы. ([21:47](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1307))

## Service в Kubernetes

Под пересоздаётся с новым IP, поэтому к нему не обращаются напрямую. Service даёт группе подов стабильное имя и виртуальный IP, подробно - [[sre-P02-основы-kubernetes#Сеть|P02]] и [[devops-L06-service-пробы-ingress#Service даёт репликам одно имя и адрес|DevOps L06]]. ([23:16](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1396))

```text
клиент -> DNS checkout -> ClusterIP -> kube-proxy / eBPF -> один из готовых подов
контроллер: Service (selector) -> EndpointSlice (IP + порт + готовность) -> сетевые правила
```

EndpointSlice - схема управления, а не звено на пути каждого пакета: контроллер обновляет его при создании, удалении и смене готовности пода, а kube-proxy переписывает по нему правила. ([31:22](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1882))

Readiness-проба решает, пускать ли новый трафик в под. Не прошедший её под помечается в EndpointSlice как неготовый, но уже открытые соединения сразу не рвутся: это зависит от сетевой реализации и приложения. Аккуратное завершение старых соединений в записи названо "медленной деградацией" [?] термин. ([44:32](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=2672), [47:13](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=2833))

| Тип          | Что даёт                                                       |
| ------------ | -------------------------------------------------------------- |
| ClusterIP    | виртуальный IP только внутри кластера, тип по умолчанию        |
| NodePort     | порт 30000-32767 на узлах, запрос дойдёт до пода на любой ноде |
| LoadBalancer | внешний балансировщик от облака или MetalLB                    |
| Headless     | `clusterIP: None`, DNS отдаёт IP всех подов                    |

([27:48](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=1668))

- NodePort - только окно наружу, сам он не балансирует между узлами.
- Kubernetes не создаёт внешний балансировщик сам: без контроллера LoadBalancer остаётся без внешнего IP.
- Headless - обнаружение экземпляров, а не балансировщик: клиент сам идёт в нужную реплику БД, например `mysql-0`.

Все типы Service работают на L4 и не умеют отправить `/orders` и `/payments` в разные сервисы: для этого нужен вход по HTTP. ([43:46](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=2626))

## Вход по HTTP: Ingress и Gateway API

Ingress и Gateway API выбирают сервис по домену и пути, а Service уже выбирает под. Оба - только правила, которые исполняет контроллер с прокси (nginx, Envoy). Gateway API гибче: веса версий, заголовки, роли админа и разработчика ([[sre-P08-стратегии-деплоя#Gateway API вместо Ingress|P08]]), но Ingress не вытеснен, особенно в легаси. ([48:39](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=2919), [51:04](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=3064))

```yaml
kind: HTTPRoute
spec:
  parentRefs:
    - name: public-gateway
  rules:
    - matches:
        - path: {type: PathPrefix, value: /api/payments}   # и /api/payments/123
      backendRefs:
        - name: payment          # Service должен существовать
          port: 80
```

## Наблюдение и диагностика входа

У точки входа смотрят нагрузку (запросов/с), ошибки 4xx и 5xx, задержку p50/p95/p99, активные соединения и сбои. Шлюз видит только HTTP: 502 бывает от сбоя связи прокси с бэкендом, а 200 может нести бизнес-ошибку, поэтому метрики шлюза дополняют метриками и логами приложения ([[sre-P04-логи-и-метрики]]). ([01:10:03](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=4203))

Сбой ищут по пути запроса, а не массовым перезапуском: например, сервису не назначился внешний IP. ([01:12:01](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=4321))

```bash
kubectl get gateway,httproute -A
kubectl describe httproute checkout-route
kubectl get svc,pods,endpointslices
```

В демо на minikube с Envoy Gateway после `kubectl scale` до 1 и обратно до 2 реплик ответы шли с одного, потом снова с двух подов. ([01:24:01](https://tbank.ktalk.ru/recordings/EQrK1k3w5gwtrsLPCl29?t=5041))
