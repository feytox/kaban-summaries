# L04. Архитектура надёжных сервисов

## Лекция как чеклист

Эта и следующая лекции - чеклист: по каждому пункту осознанно решить, нужен ли он. Делать всё не надо: лишняя сложность сама приносит баги. ([05:51](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=351))

## Зависимости

**База данных - такая же зависимость**, как любой сервис: к ней ходят по сети, она может ошибаться, тормозить и молчать. ([08:22](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=502))

### Ошибка

([09:38](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=578))

| Ожидаем                                                   | Бывает без подготовки                                 |
| --------------------------------------------------------- | ----------------------------------------------------- |
| понятная ошибка: какая зависимость чем ответила           | испорченные данные                                    |
| альтернатива: кэш, SMS вместо push (дорого, но доступнее) | ретраи забивают ресурсы, деградируют соседние функции |
| пропуск необязательного: страница без рекомендаций        |                                                       |

- обходной путь и пропуск считать метрикой, чтобы заметить рост

### Медленный ответ

Замедление хуже ошибки: тесты его не ловят, а 5 -> 8 мс могут исчерпать пул соединений и уронить весь сервис. ([16:58](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1018))

- соединение (HTTP/1.1) занято до ответа, поэтому запрос дольше держит слот пула и место в очереди
- SLA зависимости на 50 мс не спасёт: рост среднего с 5 до 10 мс уже опасен ([20:28](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1228))
- часто тормозит **один инстанс**: телеметрия по вызовам должна это показать

### Нет ответа

Без таймаута пулы забиваются, а сервис молчит почти без ошибок. Нужны таймаут и счётчик таймаутов. ([23:02](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1382))

- щедрый таймаут (100 мс при норме 5) не спасает от одной молчащей ноды: нужен выключатель

### Таймауты

([25:17](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1517))

| Таймаут                 | На что                                    |
| ----------------------- | ----------------------------------------- |
| на установку соединения | соединение зависло при подключении        |
| на вызов                | ожидание ответа после подключения         |
| сквозной (дедлайн)      | вся цепочка A -> B -> C в бюджете клиента |

- **дедлайн** передают вниз по цепочке как остаток бюджета, а не абсолютное время: часам на разных машинах доверять нельзя ([28:12](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1692))

## Повторы

Повтор оправдан только при **единичной временной ошибке**: умерла одна нода, ответ "перегружен". ([29:37](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1777))

- при массовом сбое даже один повтор удваивает нагрузку
- если повторяет каждый сервис цепочки, нагрузка на глубокий бэкенд растёт экспоненциально: повторы ставят только в выбранных узлах ([32:24](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=1944))
- **по лектору, повторять один раз**: временная ошибка пройдёт с первого повтора, иначе сбой долгий; экспоненциальное затухание многих попыток он не советует ([33:46](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2026))
- **jitter** - случайная задержка (например, 20-50 мс), чтобы повторы всех клиентов не ударили одновременно

**Идемпотентная операция** - повтор даёт тот же итоговый эффект, что и однократное выполнение. Повторять можно только такие. ([35:49](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2149))

- повтор после таймаута опасен: неизвестно, выполнилась ли операция (см. [[sre-L03-распределённые-системы#Молчание - не ответ]])
- запись делают идемпотентной через **идентификатор операции**: клиент шлёт тот же id при повторе, исполнитель проверяет, не обработал ли его ([37:35](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2255))
- при нескольких серверах реестр id общий и хранится на окно повторов

## Выключатели

**Выключатель (circuit breaker)** - при массовых ошибках прекращает поток вызовов к зависимости, а не повторяет их. ([40:45](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2445))

- сложнее всего обратное включение: вручную по алерту или автоматически по пробным запросам
- поток возобновляют со случайной паузой, иначе все клиенты включатся одновременно

## Запуск и переподключение

- урок сбоя банкоматов: после сетевого сбоя все разом переподключались и снова роняли сервер; спасло включение по группам ([43:05](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2585))
- приложение должно **стартовать без зависимостей**, включая БД: иначе после массового сбоя циклические зависимости не дадут его поднять ([46:28](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2788))
- до подключения отвечать "не готов" (в Kubernetes - readiness probe)
- переподключаться редко и со случайным смещением: подключение часто тяжелее запроса

## Исчерпаемые ресурсы

Память, диск, очереди, кэши, пулы соединений и потоков, файловые дескрипторы, порты. ([49:46](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=2986))

- неожиданные пределы: число адресов в DNS-записи для резолвера партнёров в AWS, int32-идентификаторы, длина URL в браузере ([51:16](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=3076))

## Лимиты

**Всё должно быть лимитировано**: лимит даёт понятную ошибку одному клиенту вместо падения для всех. ([55:21](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=3321))

| Технические               | Функциональные            |
| ------------------------- | ------------------------- |
| размер запроса и ответа   | число карт у клиента      |
| размер очереди            | товаров в корзине         |
| число порождаемых вызовов | подписок, участников чата |

- клиент с ~200 картами открыл экран, породивший 200 x 200 вызовов, и уронил систему для всех

## Аномальная нагрузка

Нагрузка бывает в разы выше расчётной. Сервис должен отказывать контролируемо (rate limit), а после - вернуться к норме. ([59:54](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=3594))

- очередь не бесплатный буфер: временные пароли и уведомления об операциях - в разные очереди; пароль, не доставленный за минуту, выбрасывать ([01:03:24](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=3804))
- после рестарта кэши пусты и под нагрузкой приложение не стартует: снять трафик балансировщиком, прогреть кэши, вернуть трафик ([01:08:29](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=4109))

Нагрузочный тест в три шага ([01:05:20](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=3920)):

1. Рабочий максимум: требования выполнены.
2. Пик в 3-5 раз выше (интуиция лектора): предсказуемый отказ, данные и соседи целы.
3. Возврат к максимуму: сервис восстановился; многие сами не возвращаются.
