# P08. Стратегии деплоя

## Скорость против безопасности

Частый деплой быстрее приносит фичи и обратную связь, а маленькое изменение проще откатить и расследовать. Но с ним выше риск притащить баг на прод, поэтому нужны тесты, наблюдаемость и быстрый откат. ([[sre-P08-transcript|03:30]])

**Стратегия деплоя** - способ выкатывать часто и при этом не ронять прод и откатываться за секунды. ([[sre-P08-transcript|04:15]])

Прежде стратегии выбирают индикаторы влияния, по которым её оценят: ([[sre-P08-transcript|06:48]])
- качественные: нулевой простой, тест на реальных пользователях, выбор целевой аудитории
- количественные: стоимость (ресурсы), длительность отката, вред пользователям, сложность настройки

## Gateway API вместо Ingress

По семинаристу, Ingress устарел и разработчики Kubernetes прекращают его поддержку. По документации API Ingress заморожен: его не развивают, но удалять не планируют, а для нового рекомендуют Gateway API (вне конспекта, [документация](https://kubernetes.io/docs/concepts/services-networking/ingress/)). ([[sre-P08-transcript|12:12]])

Ingress описывает пару "хост + путь", а гибкую маршрутизацию каждый контроллер делает своими аннотациями. В Gateway API веса, матчи по заголовкам и зеркалирование есть из коробки и переносимы; по семинаристу, ценой этого он медленнее Ingress под высокой нагрузкой. ([[sre-P08-transcript|12:40]])

Gateway API делит ответственность по ролям, и стратегии деплоя меняют только HTTPRoute (см. также [[sre-P02-основы-kubernetes#Сеть|P02]]): ([[sre-P08-transcript|13:58]])

```text
GatewayClass   каким контроллером обслуживается   - провайдер (здесь Envoy Gateway)
  Gateway      точка входа: адрес, порты, TLS     - администратор кластера
  HTTPRoute    куда и какой трафик идёт           - разработчик приложения
  backendRefs  Services с весами -> поды разных версий
```

Трафик HTTPRoute дробит тремя механизмами: ([[sre-P08-transcript|16:17]])

| Механизм             | Что делает                                 | Стратегия          |
| -------------------- | ------------------------------------------ | ------------------ |
| weight               | доля трафика на каждый backend             | Canary, Blue/Green |
| match                | backend по заголовку, query, методу, пути  | A/B                |
| filter RequestMirror | копия запроса на другой backend            | Shadow             |

## Rolling и Recreate: один Deployment

Эти стратегии трафик не дробят: Kubernetes меняет поды одного Deployment по очереди или разом. ([[sre-P08-transcript|24:44]])

```yaml
spec:
  replicas: 6
  strategy:
    type: RollingUpdate     # по умолчанию в Kubernetes
    rollingUpdate:
      maxSurge: 1           # сначала поднять лишний под: стабильность важнее ресурсов
      maxUnavailable: 0     # не гасить старый, пока новый не Ready
# maxSurge: 0 - сначала гасят старый под; экономит ресурсы, но при одном поде трафик оборвётся
# kubectl rollout undo deploy/my-app - откат, такая же постепенная раскатка
```

По семинаристу, новый под считается запущенным, когда прошли liveness- и readiness-пробы. По документации он доступен, когда Ready и продержался `minReadySeconds`, а Ready решает readiness-проба (вне конспекта, [документация](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)). ([[sre-P08-transcript|25:19]])

**Rolling update** - поды новой версии постепенно заменяют старые без простоя. По семинаристу, его берут в 90% случаев за простоту. ([[sre-P08-transcript|29:28]])
- во время раскатки v1 и v2 работают одновременно: нужна [[sre-L05-монолиты-и-микросервисы#Совместимость версий|совместимость версий]]

**Recreate** - сначала удалить все поды, потом поднять новую версию. Его берут, когда одновременная работа v1 и v2 недопустима: несовместимые схемы данных, общий эксклюзивный ресурс, вендорская "коробка" с миграцией без отката. ([[sre-P08-transcript|32:11]])
- простой длится время остановки плюс запуска, а с миграцией намного дольше
- откат тоже с простоем

## Blue/Green и Canary: две версии, веса

Обе версии подняты отдельными Deployment и Service, а трафик между ними переключает только HTTPRoute. ([[sre-P08-transcript|36:01]])

```yaml
# canary: вес v2 меняют 10 -> 50 -> 100 по мере уверенности, откат - обнулить вес
rules:
  - backendRefs:
      - name: my-app-v1
        port: 80
        weight: 90
      - name: my-app-v2
        port: 80
        weight: 10
# blue/green: в маршруте один backendRef; apply маршрута на my-app-v2 переключает всех разом,
# apply маршрута на my-app-v1 - мгновенный откат
```

**Blue/Green** - новую версию целиком разворачивают рядом со старой, выполняют миграции и разом переключают на неё весь трафик. Старая простаивает, готовая к мгновенному откату. ([[sre-P08-transcript|36:14]])
- цена - x2 ресурсов, большую часть времени половина простаивает
- баг новой версии заденет сразу всех

Миграция БД blue/green не мешает, если у каждой версии своя база. Перед переключением прогревают кэши: иначе резко вырастет нагрузка на базу. ([[sre-P08-transcript|40:59]])

**Canary** - новая версия получает малую долю реального трафика; по метрикам ошибок и латентности долю увеличивают или обнуляют. От rolling её отличает управляемое промежуточное состояние: долю можно держать на 10% сколько нужно. ([[sre-P08-transcript|44:44]])
- на новую версию попадает случайный пользователь, выбрать кого нельзя
- нужна наблюдаемость, чтобы вовремя заметить деградацию

Версии работают одновременно, поэтому миграция БД при канарейке недопустима: пользователи новой версии не заполнят поля старой, и при откате эти данные потеряются. ([[sre-P08-transcript|18:22]])

По семинаристу, канарейка не требует лишнего железа, а в таблице на слайде её стоимость "средняя" [?] источники расходятся. Откат на слайде быстрый, а в итогах семинарист назвал его очень долгим [?] причину не пояснил. ([[sre-P08-transcript|01:06:34]])

## A/B и Shadow: точная аудитория и копия трафика

**A/B testing** - канарейка, где аудиторию выбирают точно: по заголовку, cookie, query-параметру, гео. Так фичу дают сотрудникам банка или пользователям Safari; по слайду это скорее инструмент продуктового решения, чем стратегия деплоя. ([[sre-P08-transcript|54:17]])

```yaml
rules:
  - matches:
      - headers:
          - type: Exact
            name: x-user-group
            value: beta
    backendRefs:
      - name: my-app-v2   # группа beta получает новую фичу
        port: 80
  - backendRefs:
      - name: my-app-v1   # все остальные - как было
        port: 80
```

**Shadow** - пользователь получает ответ старой версии, а копия его запроса уходит на новую, и её ответ отбрасывается. Новую версию проверяют органическим трафиком без риска для пользователей, но обе версии нагружены одновременно. ([[sre-P08-transcript|59:39]])

```yaml
rules:
  - backendRefs:
      - name: my-app-v1        # отвечает пользователю
        port: 80
    filters:
      - type: RequestMirror
        requestMirror:
          backendRef:
            name: my-app-v2    # получает копию, ответ отбрасывается
            port: 80
```

## Какую стратегию брать

Сравнение со слайда: ([[sre-P08-transcript|01:04:43]])

| Стратегия  | Простой | Стоимость  | Скорость отката | Контроль трафика | Сложность |
| ---------- | ------- | ---------- | --------------- | ---------------- | --------- |
| Recreate   | есть    | низкая     | медленно        | нет              | низкая    |
| Rolling    | нет     | низкая     | медленно        | нет              | низкая    |
| Blue/Green | нет     | x2 ресурсы | мгновенно       | всё или ничего   | средняя   |
| Canary     | нет     | средняя    | быстро          | доля (вес)       | средняя   |
| A/B        | нет     | средняя    | быстро          | точная аудитория | высокая   |
| Shadow     | нет     | x2 ресурсы | -               | копия трафика    | высокая   |

Канарейку многие считают серебряной пулей, её сложность по семинаристу на деле невысокая.
