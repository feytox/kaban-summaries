# L03. Распределённые системы

Лекция не записывалась: заметка собрана по конспекту и слайдам с сайта лектора, устные комментарии - из повторения в начале [[sre-L04-архитектура-надёжных-сервисов|L04]].

## Сервис - распределённая система

**Распределённая система** - несколько независимых узлов, которые обмениваются сообщениями и вместе предоставляют сервис. Узлы - процессы, приложения, серверы или датацентры; пользователь видит один сервис. ([[sre-L03-slides#Слайд 2|слайд 2]])

| Участок               | Свойство сети                       |
| --------------------- | ----------------------------------- |
| внутри датацентра     | задержка низкая, сбои возможны      |
| между датацентрами    | задержка обычно выше, бывают потери |
| с партнёрами          | чужая сеть, меньше контроля         |
| до мобильного клиента | связь может пропасть надолго        |

- сеть ненадёжна на любом расстоянии: запрос или ответ может задержаться или потеряться
- **мобильное приложение - полноценная часть системы**: офлайн-работа клиента требует отдельных решений ([[sre-L03-slides#Слайд 4|слайд 4]])
	- лектор: бэкендеры думают только о серверах, а с ним спорят, что теоремы не про мобильные; эффекты там те же ([02:13](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=133))

**Метод "маленьких человечков"** - представить узлы людьми, которые обмениваются сообщениями, и проследить, кто что знает и какое сообщение до кого дошло. Это способ рассуждать, а не утверждение, что компьютеры устроены как люди. ([[sre-L03-slides#Слайд 5|слайд 5]])

## Договориться

Договориться - значит, что узлы выбирают **одно и то же значение**, а исправные узлы в итоге получают результат. ([[sre-L03-slides#Слайд 6|слайд 6]])

- выбрать исполнителя: все узлы считают, что задачу выполняет один и тот же узел
- изменить счётчик: запросы пришли в разные узлы, система решает, какие изменения учесть и в каком порядке

### Молчание - не ответ

Клиент видит один и тот же таймаут в трёх разных ситуациях ([[sre-L03-slides#Слайд 7|слайд 7]]):

| Что случилось       | Выполнена ли операция |
| ------------------- | --------------------- |
| запрос не дошёл     | нет                   |
| сервер ещё работает | пока нет              |
| ответ не дошёл      | возможно, да          |

- таймаут не доказывает, что операция не состоялась
- повтор запроса может выполнить действие второй раз, поэтому системе нужен способ распознать повтор (см. [[sre-L04-архитектура-надёжных-сервисов#Повторы]])

### Меньше согласования

Если узлы больше решают сами, системе реже приходится ждать общего решения. Это не замена согласованию, а способ требовать его реже или по другим правилам. ([[sre-L03-slides#Слайд 8|слайд 8]])

| Подход   | Как обходится с согласованием                                                   |
| -------- | ------------------------------------------------------------------------------- |
| UUID     | идентификаторы создаются локально; совпадение крайне маловероятно, но возможно  |
| Git      | изменения готовят независимо и объединяют; конфликты разрешают вручную          |
| CRDT     | независимые изменения сливаются по правилам; после доставки всех копии сходятся |
| Блокчейн | общий протокол консенсуса: меняет способ согласования, но не убирает его        |

**CRDT** - типы данных, в которых независимые изменения объединяются по заданным правилам.

### Координатор

Один участник принимает решения за остальных, как организатор встречи или дирижёр: логика проще, но он - точка отказа. ([[sre-L03-slides#Слайд 9|слайд 9]])

- пока координатор недоступен, никто не знает, кто принимает решения
- частый гибрид: выбрать **лидера** распределённым алгоритмом и при его потере выбрать нового
- протокол должен исключать конфликтующие решения старого и нового лидеров

## CAP

CAP описывает выбор при **сетевом разделе** - когда группы узлов не могут обмениваться сообщениями. ([[sre-L03-slides#Слайд 10|слайд 10]])

| Буква | Свойство                                    | Смысл в теореме                                                                       |
| ----- | ------------------------------------------- | ------------------------------------------------------------------------------------- |
| C     | Consistency, согласованность                | линейризуемость: операции выглядят выполненными по одной, в порядке реального времени |
| A     | Availability, доступность                   | каждый корректный запрос к исправному узлу в итоге получает результат, а не отказ     |
| P     | Partition tolerance, устойчивость к разделу | система учитывает потерю связи между группами узлов, сами узлы продолжают работать    |

- C: если запись завершилась до начала чтения и новых записей нет, чтение с любого узла вернёт записанное
- A здесь не процент за период, как в [[sre-L01-надёжность-и-доступность#Надёжность и доступность|L01]], и без верхней границы времени ответа

При разделе нельзя гарантировать и C, и A: узел не знает, нет ли в другой группе более нового изменения. ([[sre-L03-slides#Слайд 11|слайд 11]])

| Поведение | При разделе                                                   |
| --------- | ------------------------------------------------------------- |
| CP        | отказать в операции или ждать связи, сохранив согласованность |
| AP        | продолжать отвечать, допуская расхождение копий               |

- по лектору, пока связь есть, система может быть и согласованной, и доступной; выбирать приходится только при разделе ([01:32](https://tbank.ktalk.ru/recordings/g9O9Jc2bvn4IdGpQFmFn?t=92))
- последующее согласование копий в AP требует своих правил: CAP его не гарантирует
- CP/AP - описание выбора при разделе, а не ярлык, полностью характеризующий систему

### Мобильный клиент офлайн

([[sre-L03-slides#Конспект|конспект]])

- выбор зависит от смысла операции и делается заранее
- действие должно сразу изменить общее значение: дождаться связи или сообщить, что действие пока недоступно (CP)
- приложение принимает изменения офлайн: после связи их сопоставляют с сервером и разрешают конфликты (AP)

## PACELC

PACELC дополняет CAP обычной работой: **если раздел (P)**, выбор между A и C, **иначе (E)** - между задержкой (L) и согласованностью (C). ([[sre-L03-slides#Слайд 13|слайд 13]])

- даже при исправной сети ожидание подтверждений увеличивает задержку, а быстрый ответ требует ослабить согласованность
- бесплатного выбора нет: решают для конкретного сервиса и конкретной операции

Пропущено: иллюстрации, аналогия с договорённостью о встрече, вопросы для самопроверки.
