# P03. Логирование

Логи - фундамент наблюдаемости: от их качества зависит, сколько часов уйдёт на диагностику сбоя. В разобранных на семинаре крупных сбоях (Cloudflare, Datadog, Knight Capital) сигналы о проблеме были, но не хватило правильных логов и алертов. ([05:01](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=301))

## Что писать в лог

### Уровень

Уровень обязателен в каждой записи: без него не понять, насколько всё плохо. ([06:03](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=363))

| Уровень | Когда ставить                                                |
| ------- | ------------------------------------------------------------ |
| Fatal   | приложение не может продолжать работу                        |
| Error   | пользователь не получил услугу из-за внутренней ошибки       |
| Warn    | внешняя система ответила неожиданно, или сбой обошли ретраем |
| Info    | редкие штатные события: старт, перечитали конфиг             |
| Debug   | вызовы внешних систем, обработка запросов                    |
| Trace   | всё, что можно                                               |

На проде никогда не включают Debug и Trace: это огромная нагрузка на сборщики логов. Уровень задают переменной окружения при деплое, например Debug локально и Info на проде. ([58:40](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3520))

### Формат

На проде логи пишут в JSON: его разбирает почти любой инструмент, и он поддерживает вложенные поля. Неструктурированный текст и logfmt удобны только при локальной разработке: текст приходится разбирать регулярками, которые ломаются от любой правки сообщения, а logfmt не умеет вложенность. ([09:06](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=546))

### Поля

Имена полей берут из OpenTelemetry Semantic Conventions: ([11:24](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=684))
- **Когда и что:** `timestamp` в ISO 8601 и UTC с миллисекундами, `level`, `message`.
- **Кто и где:** `service.name`, `service.version`, окружение `deployment.environment.name`, реплика `host.name` или `k8s.pod.name`.
- **Связь записей:** `trace_id` и `request_id`, чтобы собрать все строки одного запроса.
- **По ситуации:** `duration_ms`, `error.message`, `error.stack`.

По семинаристу, окружение и дата-центр в большой компании добавляет коллектор логов, а в стартапе их приходится писать самому. ([01:04:19](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3859))

### Шаблон сообщения

Уникальные значения вроде ID заказа не вставляют в текст сообщения, иначе одинаковые события не сгруппировать без регулярок. Их выносят в отдельные поля, а в сообщении оставляют шаблон: `"Order {order_id} failed"` и поле `"order_id": 42`. ([14:05](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=845))

**Кардинальность** - число уникальных значений поля. У метрик она должна быть низкой: каждое новое значение лейбла создаёт новый временной ряд, и база метрик может упасть по памяти. Логи - отдельные события, и для них высокая кардинальность (`request_id`) нормальна. ([15:04](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=904))

## Чувствительные данные

Чего нельзя писать в логи: ([17:16](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1036))
- секреты: пароли, токены, ключи, строки подключения к БД;
- CVV и PIN, даже маскированные; номер карты допустим только в виде первых 6 и последних 4 цифр;
- персональные и медицинские данные;
- session id в открытом виде: по нему можно войти в чужой аккаунт, поэтому пишут хэш.

Способы скрыть значение: ([19:41](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1181))
- **Удалить** поле или заменить на `[REDACTED]`.
- **Замаскировать** часть: `411111******1234`.
- **Хэшировать.** Значение скрыто, но записи с ним можно связать между собой; так логируют, например, email.
- **Токенизировать.** Значение заменяют токеном, а оригинал хранят в Vault. Используют редко.
- **Зашифровать** отдельное поле.
- **Запретить в логгере** список полей, чтобы разработчик не мог залогировать их даже случайно.

Маскировать можно в логгере приложения или в коллекторе, например в Vector. Коллектор - только последний рубеж: до него секрет уже записан в лог на ноде, и тот, кто получит к ней доступ, его прочитает. ([22:48](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1368))

## Сбор логов

Хранить логи файлами на серверах и искать grep'ом можно, пока сервер один. Дальше непонятно, где искать, а ротация через несколько дней стирает следы. Поэтому логи собирают в централизованное хранилище с поиском и визуализацией. ([25:43](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1543))

Логи собирают агенты: самые лёгкие из них Fluent Bit и Vector, самый тяжёлый Logstash. Агент работает как конвейер из трёх шагов: input (собрать), filter (преобразовать), output (отправить). Vector в ДЗ настраивается так же. ([30:40](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1840))

**OTLP** - протокол OpenTelemetry, который одинаково передаёт логи, метрики и трейсы и не привязан к вендору. ([28:58](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1738))

### Доставка логов в Kubernetes (вне конспекта)

На семинаре способы доставки только перечислили в ДЗ. Ниже - по [документации Kubernetes](https://kubernetes.io/docs/concepts/cluster-administration/logging/).

Контейнерный рантайм пишет stdout и stderr каждого контейнера в файлы в `/var/log/pods` на ноде. Отсюда три способа доставки:
- **Агент на ноде (DaemonSet)** читает эти файлы для всех подов ноды.
	- Плюсы: на ноду нужен один агент, приложение менять не надо.
- **Sidecar с агентом** работает в каждом поде рядом с приложением.
	- Плюсы: агента можно настроить под конкретное приложение.
	- Минусы: агент в каждом поде тратит много ресурсов, и `kubectl logs` этих логов не видит.
- **Push из приложения**: приложение само отправляет логи в хранилище.
	- Документация считает этот способ вне зоны ответственности Kubernetes.

Что происходит с логами пода:
- **Контейнер перезапустился.** kubelet хранит логи одного предыдущего контейнера, их показывает `kubectl logs --previous`.
- **Под удалили или вытеснили с ноды.** Его логи на ноде удаляются вместе с контейнерами.
- **Логов много.** Файлы ротируются, по умолчанию до 5 файлов по 10 MiB на контейнер.

Поэтому у логов должно быть своё хранилище, которое живёт независимо от подов и нод.

## Хранилища логов

Хранилища различаются тем, что индексируют: ([32:18](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1938))
- **Полнотекстовый индекс** (Elasticsearch, OpenSearch) индексирует почти всё.
	- Плюсы: самый мощный поиск с ранжированием по релевантности.
	- Минусы: тяжёлый, индекс бывает больше самих данных.
- **Индекс по лейблам** (Loki) индексирует только метки, а логи хранит сжатыми в S3.
	- Плюсы: дёшево и просто.
	- Минусы: поиск по тексту без фильтра по лейблам просматривает все логи.
- **Колоночное хранение** (ClickHouse, Victoria Logs).
	- Плюсы: компактно, быстрые фильтры и агрегации.
	- Минусы: нет ранжирования по релевантности.

Выбор на примерах из семинара: ([40:11](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2411))
- 30 сервисов в Kubernetes, хранить год, бюджет минимальный, ищут по сервису и поду -> Loki, потому что сервис и под и есть лейблы.
- Поддержка ищет по тексту обращений и хочет ранжирование -> Elasticsearch.
- Нужно считать долю ошибок и p95 по 500 GB логов за неделю -> ClickHouse или Victoria Logs.

**ELK** - стек из Elasticsearch (хранение и поиск), Logstash (обработка) и Kibana (интерфейс). Начать с него легко, но на больших объёмах он требует много ресурсов и опыта. ([37:14](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2234))

## Victoria Logs

**Victoria Logs** - колоночная БД для логов от команды VictoriaMetrics. ([41:37](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2497))
- Это один бинарник с открытой лицензией.
- Она принимает логи по протоколам Elasticsearch и Loki, поэтому сборщик менять не нужно.
- В ней есть встроенный веб-интерфейс vmui (`/vmui/`).
- Она хранит логи по дням и сжимает их в 10 раз и больше. По умолчанию логи живут 7 дней.

По семинаристу, логи в Т-Банке хранятся на стеке VictoriaMetrics, а индустрия движется к колоночным хранилищам. ([57:04](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3424))

### Служебные поля

У каждой записи три служебных поля: ([46:37](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2797))
- **`_msg`** - текст сообщения. По нему ищет фильтр без имени поля; это единственное обязательное поле.
- **`_time`** - время события. Если его нет, берётся время приёма. Почти каждый запрос начинают с фильтра `_time:`, иначе просматривается весь срок хранения.
- **`_stream`** - набор полей-меток, как лейблы в Loki. Логи одного стрима лежат на диске рядом, поэтому запросы по ним быстрые.

Менять формат логов приложения не нужно: в настройках сборщика указывают, какое поле считать `_msg`, `_time` и `_stream`. ([48:17](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2897))

```toml
[sinks.vlogs.query]
_msg_field = "message"
_time_field = "timestamp"
_stream_fields = "appname"
```

### LogsQL

Запрос состоит из фильтра и цепочки пайпов через `|`, как в Unix. ([49:08](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2948))

```
error                                  # поиск слова в _msg
_time:5m level:error -(buggy OR foo)   # окно, поле, исключение
_time:5m level:error | sort by (_time) desc | limit 10

# доля ошибок по сервису - готовое условие для алерта
_time:5m
  | stats by (service.name) count() logs, count() if (level:error) errors
  | math (errors / logs) as error_rate
  | filter error_rate:>0.1
```

Для агрегаций есть `top`, `quantile(0.95, поле)` и `count_uniq`.

Сама Victoria Logs алерты не отправляет. Запрос по расписанию выполняет vmalert, а уведомления в звонки и Telegram рассылает Alertmanager. ([54:20](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3260))
