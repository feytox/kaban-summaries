# P03. Логирование

## Зачем хорошие логи

В сбоях Cloudflare (2023), Datadog (2023) и Knight Capital (2012) сигналы были, но не хватило правильных логов и алертов, независимых от продакшена. Datadog, например, обновлением systemd уронил и прод, и собственный мониторинг. Логи - фундамент наблюдаемости: от их качества зависит, сколько часов уйдёт на диагностику. ([01:46](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=106))

## Уровни логирования

Уровень обязателен в каждой записи: без него не понять, насколько всё плохо. ([06:03](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=363))

| Уровень | Когда                                                       |
| ------- | ----------------------------------------------------------- |
| Fatal   | приложение не может продолжать работу                       |
| Error   | пользователь не получил услугу из-за внутренней ошибки      |
| Warn    | неожиданный ответ внешней системы; сбой, обойдённый ретраем |
| Info    | редкие штатные операции: старт, перечитали конфиг           |
| Debug   | вызовы внешних систем, обработка запросов                   |
| Trace   | всё, что можно                                              |

([01:00:35](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3635))
- прод никогда не работает на Debug и Trace: это огромная нагрузка на сборщики и мусор
- уровень задают при деплое переменной окружения: локально Debug, на проде Info ([58:40](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3520))

## Формат и содержание

| Формат              | Плюсы                                 | Минусы                                  |
| ------------------- | ------------------------------------- | --------------------------------------- |
| неструктурированный | читается как есть                     | regex-парсинг ломается от правки текста |
| logfmt              | читаемо, на 30-40% компактнее JSON    | плоский, без вложенности                |
| JSON                | парсится почти всем, есть вложенность | чуть больше объём                       |

JSON - для прода, logfmt и текст - для локальной разработки. ([09:06](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=546))

Что класть в лог (имена полей из OpenTelemetry Semantic Conventions): ([11:24](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=684))
- `timestamp`: ISO 8601, UTC, до миллисекунд
- `level`, `message`
- кто и где: `service.name`, `service.version`, `deployment.environment.name`, `host.name` или `k8s.pod.name`
- `trace_id`, `request_id`: склеить все строки одного запроса
- `duration_ms`, `error.message`, `error.stack`: где осмысленно

По семинаристу, окружение и ДЦ в большой компании дописывает коллектор, а в стартапе их логируют сами. ([01:04:19](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3859))

Уникальные значения (ID заказа, запроса) не пишут в текст сообщения, иначе записи не сгруппировать без regex. Их выносят в поля, а в сообщении оставляют шаблон: `"Order {order_id} failed"` + `"order_id": 42`. ([14:05](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=845))

**Кардинальность** - число уникальных значений поля. У лейблов метрик она должна быть низкой, иначе число временных рядов взрывается и TSDB падает по памяти. Логи и трейсы - отдельные события, для них высокая кардинальность (`request_id`) - норма. ([15:04](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=904))

## Чувствительные данные

Что нельзя логировать: ([17:16](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1036))
- секреты: пароли, токены, ключи, строки подключения к БД
- CVV и PIN - никогда; номер карты - максимум первые 6 и последние 4 цифры
- персональные и медицинские данные
- исходный код: попадает со stack trace, если в коде зашит пароль
- session id как есть: по нему входят в чужой кабинет; лучше хэш

Техники маскирования: ([19:41](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1181))
- удалить поле или заменить на `[REDACTED]`
- частично: `411111******1234`
- хэшировать: значение скрыто, но записи одного пользователя можно связать (так логируют email)
- токенизировать: оригинал лежит в Vault; редко
- шифровать отдельное поле
- deny-list в логгере: запрещённое поле физически не залогировать

Маскировать можно в логгере приложения или в коллекторе (Vector `redact()`). Коллектор - только последний рубеж: секрет всё равно остаётся в логе на ноде. ([22:48](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1368))

## Сбор и транспорт

Логи в файле и grep годятся стартапу. С несколькими серверами непонятно, где искать, а ротация через пару дней стирает следы. Поэтому логи собирают в централизованное хранилище с поиском и визуализацией. ([25:43](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1543))

Агенты по потреблению ресурсов: Fluent Bit ≈ Vector < Filebeat ≈ OTel Collector < Fluentd < Logstash. ([28:05](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1685))

Транспорт: syslog (RFC 5424) и **OTLP** - вендор-независимый протокол OpenTelemetry сразу для логов, метрик и трейсов поверх HTTP или gRPC.

Преобразовать логи можно в приложении, агенте, промежуточном звене (Logstash) или хранилище. Агенты работают пайплайном input -> filter -> output; Vector в ДЗ настраивается так же. ([29:56](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1796))

### Доставка логов в Kubernetes (вне конспекта)

На семинаре способы только перечислены в ДЗ. По [документации Kubernetes](https://kubernetes.io/docs/concepts/cluster-administration/logging/):

| Способ             | Как                                      | Плюсы                                      | Минусы                                     |
| ------------------ | ---------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| агент на ноде      | DaemonSet читает файлы логов контейнеров | один агент на ноду, приложение не меняется | -                                          |
| sidecar с агентом  | агент в каждом поде                      | свой конфиг под приложение                 | много ресурсов, `kubectl logs` их не видит |
| push из приложения | приложение само шлёт в хранилище         | -                                          | вне зоны Kubernetes                        |

- рантайм пишет stdout и stderr контейнеров в файлы в `/var/log/pods` на ноде
- при перезапуске контейнера kubelet хранит логи одного предыдущего: `kubectl logs --previous`
- когда под вытесняют с ноды, его логи удаляются вместе с контейнерами
- файлы ротируются (по умолчанию 5 файлов по 10 MiB), `kubectl logs` видит только последний
- поэтому у логов должно быть хранилище с жизненным циклом, независимым от подов и нод

## Хранилища логов

| Тип                   | Примеры                   | Плюсы                        | Минусы                               |
| --------------------- | ------------------------- | ---------------------------- | ------------------------------------ |
| полнотекстовый индекс | Elasticsearch, OpenSearch | мощный поиск с ранжированием | тяжёлый, индекс бывает больше данных |
| индекс по лейблам     | Loki                      | дёшево: сжатые чанки в S3    | поиск по тексту - полный скан        |
| колоночное            | ClickHouse, Victoria Logs | компактно, быстрые агрегации | нет ранжирования по релевантности    |

([32:18](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=1938))

Postgres не годится для логов: медленный полнотекстовый поиск, не вытянет поток. Redis держит всё в памяти, а логов терабайты. ([35:32](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2132))

**Loki** - подход Prometheus для логов: индексирует только лейблы. Кратно легче ELK и есть алертинг, но поля парсят агенты, а смотреть можно только через Grafana. ([39:18](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2358))

## Victoria Logs

Бессхемная БД для логов от команды VictoriaMetrics. ([41:37](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2497))
- один бинарник, Apache 2.0 и для single-node, и для кластера
- принимает Elasticsearch Bulk API и Loki push API: шиппер менять не нужно
- встроенный UI vmui (`/vmui/`)

Колоночное хранение с партициями по дням; логи одного стрима лежат рядом, вместо индекса bloom-фильтры. Сжатие 10x и больше, retention по умолчанию 7 дней. Против Loki на 500 GB: RAM 1,3 GB против 6-7 GB, p99 запросов в 3,6 раза быстрее. ([43:20](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2600))

Ограничения: запись до 2 MB, до 2000 полей, плохо с динамическими ключами JSON, нет ранжирования, молодая экосистема. ([45:48](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2748))

По семинаристу, логи в Т-Банке хранятся на стеке VictoriaMetrics, а индустрия движется к колоночным БД для логов. ([57:04](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3424))

### LogsQL

Запрос - фильтр, а за ним пайпы через `|`, как в Unix. ([49:08](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=2948))

```
error                                  # полнотекстовый поиск в _msg
_time:5m level:error -(buggy OR foo)   # окно, поле, исключение
_time:5m level:error | sort by (_time) desc | limit 10

# error rate по сервису - условие для алерта
_time:5m
  | stats by (service.name) count() logs, count() if (level:error) errors
  | math (errors / logs) as error_rate
  | filter error_rate:>0.1
```

Другие агрегации: `top N by (...)`, `quantile(0.95, field)`, `count_uniq(...)`.

Victoria Logs сама алерты не шлёт: цепочка Victoria Logs -> vmalert (выполняет запрос) -> Alertmanager (звонки, Telegram). Для панелей в Grafana есть официальный плагин. ([54:20](https://tbank.ktalk.ru/recordings/1uK8BHn4CGk71vj1Vaxw?t=3260))

Пропущено: подробности трёх сбоев, упражнения на поиск проблем и утечек в логах, таблица агентов, Splunk и Graylog, детали бенчмарка, демо vmui, внутренняя платформа наблюдаемости Т-Банка, ДЗ.
