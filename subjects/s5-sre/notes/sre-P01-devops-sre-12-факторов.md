# P01. DevOps, SRE и 12 факторов

## DevOps и SRE

С веб-сервисами между разработкой и эксплуатацией выросла **стена**: разработчик не знает, как приложение запущено, а админ - как оно устроено, и не может чинить баги. Ответом стал DevOps. ([36:17](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=2177))

|             | DevOps                                                     | SRE                                                      |
| ----------- | ---------------------------------------------------------- | -------------------------------------------------------- |
| Что это     | философия (2009)                                           | подход Google (книга 2016)                               |
| Отвечает на | чего достичь                                               | как достичь: `class SRE implements DevOps`               |
| Главное     | you build it, you run it; CALMS; CI/CD                     | выделенная роль; надёжность через доступность; blameless |
| Проблема    | нет единого понимания; DevOps-инженер - узкая дорогая роль | -                                                        |

([39:58](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=2398))
- **you build it, you run it** - кто собрал код, тот его запускает и поддерживает; это курс и берёт из DevOps
- **CALMS** - Culture, Automation, Lean, Measurement, Sharing (S семинарист не расшифровал, вне конспекта)
- SRE появился, потому что частые релизы дали больше сбоев, а каждый сбой у Google - это непоказанная реклама ([45:23](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=2723))
- отдельная роль SRE нужна из-за разделения труда; в стартапах её часто нет ([01:34:51](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=5691))

**Надёжность** по семинаристу - ожидание пользователей от доступности; у лектора - свойство системы про будущее ([[sre-L01-надёжность-и-доступность#Надёжность и доступность|L01]]). ([49:45](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=2985))

**Доступность** - доля времени, когда приложение работает.

Лектор считает SLA/SLO/SLI устаревшими. Семинарист согласен с этим только для **распределённых систем**; для простого веб-приложения считает их хорошими, и проберы в курсе строят на них. ([25:03](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=1503))

## Необвинительная культура

**Blameless culture** - за ошибки и сбои не наказывают: человеческий фактор не устранить, можно только снизить его влияние. ([51:42](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=3102))

**Постмортем** - разбор инцидента: причина, хронология, что сделать, чтобы не повторился. Blameless postmortem - "необвинительный", не "безупречный".

- наказание -> выгорание, страх экспериментировать, сокрытие деталей; а для разбора нужна **причина, а не виноватый** ([54:27](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=3267))
- важно **намерение**: ненамеренные ошибки (не хватило знаний, отступил от ранбука) не наказывают, умышленный вред - да
- стажёр сломал прод-БД - выясняют, почему у него был такой доступ

## 12 факторов

**12 факторов** (12factor.net) - практики для cloud native сервисов от разработчиков Heroku. Семинарист советует читать оригинал на английском: термины плохо переводятся. ([01:01:49](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=3709))

### Код и сборка

| Фактор                       | Правило                                          | Антипаттерн                                       |
| ---------------------------- | ------------------------------------------------ | ------------------------------------------------- |
| **1. Кодовая база**          | один репозиторий - много развёртываний           | одно приложение в нескольких репо                 |
| **2. Зависимости**           | объявлены в манифесте, версии зафиксированы      | системные пакеты хоста, "на моей машине работает" |
| **5. Сборка, релиз, запуск** | build -> release -> run, релиз неизменяем и с ID | сборка или правка кода в проде                    |

([01:05:04](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=3904))
- **1:** приложение в нескольких репозиториях - уже распределённая система; общий код выносят в библиотеку
- **5:** build - код в артефакт, release - артефакт + конфиг, run - запуск релиза ([01:13:11](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4391))
- **5:** ID релиза - дата или semver; без него не откатиться

### Конфигурация и окружение

| Фактор                    | Правило                                                | Антипаттерн                        |
| ------------------------- | ------------------------------------------------------ | ---------------------------------- |
| **3. Конфигурация**       | всё, что меняется между окружениями, и секреты - в env | конфиг в коде, секреты открыто     |
| **4. Сторонние сервисы**  | БД, кэш, очереди - ресурсы по адресу из конфига        | код привязан к реализации (SQLite) |
| **10. Паритет окружений** | dev, test, prod различаются только ресурсами           | dev на SQLite, prod на Postgres    |

([01:10:00](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4200))

- **4:** локальный MySQL меняется на облачный, MinIO на S3 без пересборки ([01:11:14](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4274))
- **10:** число контуров зависит от процессов: 2 при сильных автотестах, 4-5 при ручном тестировании ([01:22:30](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4950))

### Процесс в работе

| Фактор                 | Правило                                               | Антипаттерн                               |
| ---------------------- | ----------------------------------------------------- | ----------------------------------------- |
| **6. Процессы**        | stateless: данные в БД, кэше, объектном хранилище     | состояние в памяти или на локальном диске |
| **7. Привязка портов** | приложение само HTTP-сервер на порту из env           | нужен внешний Tomcat, Apache              |
| **8. Параллелизм**     | типы процессов (web, worker, cron), масштаб их числом | одна большая машина                       |
| **9. Утилизируемость** | старт за секунды, корректный SIGTERM                  | долгий прогрев, зависание на SIGTERM      |

([01:15:54](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4554))

- **6:** процесс могут убить в любой момент, в Kubernetes это норма
- **7:** исключения, которым нужен внешний сервер: Java-сервлеты, PHP ([01:17:55](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4675))
- **8:** в Kubernetes процессы масштабирует он сам; второй оркестратор поверх (Celery) мешает ([01:19:00](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4740))
- **9:** **долгий старт = сбой при всплеске трафика**: новые инстансы не успевают подняться ([01:20:35](https://tbank.ktalk.ru/recordings/FpkfTFnU3N7kk0A74otT?t=4835))
- **9:** кэш прогревают параллельно с обработкой запросов или обходятся без прогрева
