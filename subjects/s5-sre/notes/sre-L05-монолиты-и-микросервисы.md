# L05. Монолиты, микросервисы и эксплуатация

Лекция заканчивает чеклист архитектуры из [[sre-L04-архитектура-надёжных-сервисов|L04]]: по каждому пункту решают из практической целесообразности. ([00:21](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=21))

## Рестарт как штатный инструмент

Чем больше компонентов можно рестартовать в любой момент не задумываясь, тем проще жить: при сбое сначала рестартуют, а причину ищут потом. Рестарт заново поднимает соединения, очищает память и кэши, применяет новый конфиг. ([02:30](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=150))

Что рестартовать нельзя, записывают поимённо: почему нельзя и почему решили это не чинить. Иначе команда про каждый сервис скажет "не знаем" и будет рестартовать только ночью. ([09:29](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=569))

- примеры: БД, которая при старте долго проверяет индексы; потоковое распознавание речи
- нормальная остановка: перестать брать новую работу, дождаться конца начатой, потом выключать
- свой рестарт не должен ронять соседей лавиной подключений ([[sre-L04-архитектура-надёжных-сервисов#Запуск и переподключение|L04]])

Рестарт чаще помогает или ничего не меняет, но изредка усугубляет сбой: ([06:56](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=416))
- баг проявляется только при старте: проблема была на 3 нодах из 100, после рестарта - на всех
- новый конфиг подложили "до следующего рестарта" и забыли: рестарт неожиданно ломает сервис

## Совместимость версий

При раскатке, откате и у необновлённых клиентов старая и новая версии работают рядом. Поэтому API и данные держат совместимыми на несколько версий. ([10:15](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=615))

| Чьё API               | Сколько держать совместимость                                       |
| --------------------- | ------------------------------------------------------------------- |
| мобильного приложения | почти вечно: пользователи не обновляются, а принуждение отпугнёт их |
| веб-сайта             | обновлением управляете вы: пользователь загружает свежий сайт       |
| сервисов в датацентре | по прикидке лектора около 3 месяцев: столько можно откатываться     |

**Совместимость по данным** - версии из окна совместимости работают на одних и тех же данных. Её часто ломают миграции, которые удаляют или заменяют поля: откат становится невозможным или дорогим. ([12:41](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=761))

**Расширение и сужение схемы** - смена формата данных только совместимыми шагами. По лектору, так можно сделать всегда. ([13:24](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=804))

1. Добавить новое поле, старое не трогать.
2. Писать оба варианта, читать новый, а если его нет - старый.
3. Держать так несколько версий, пока откат не перестанет быть нужен.
4. Удалить старое поле отдельным изменением, потом убрать из кода его чтение.

- по конспекту лектора, откат кода не отменяет необратимых действий вроде проведённого платежа

## Сквозной ID

**Сквозной ID** - идентификатор входящего запроса, который сервис передаёт во все порождённые вызовы и пишет в логи. Его закладывают почти всегда и сразу: потом внедрить очень сложно. ([17:15](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1035))

Поиск по ID в логах показывает путь запроса через все сервисы, то есть трассировку за стоимость логов (ср. trace_id в [[sre-P04-логи-и-метрики#Практики|P04]]). Системы трассировки, по лектору, отличаются от этого почти только тем, что лучше держат нагрузку. ([19:37](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1177))

Сообщение в очереди - такой же вызов, только с возможностью полежать. Поэтому ID кладут и в каждое сообщение Kafka. ([20:54](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1254))

ID с признаком "сохранять ли логи" позволяет при миллионах запросов в секунду хранить, например, 10% запросов целиком, со всех сервисов. Случайные 10% записей в каждом сервисе бесполезны: нужны все логи одного запроса. ([22:11](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1331))

## Сервис рассказывает о себе

**Самодиагностика** - страница по стандартному адресу, где экземпляр сам рассказывает о своём состоянии. Это удобнее усреднённых графиков в Grafana: если не отвечает одна нода, открывают её страницу. ([29:51](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1791))

- сам ответ страницы показывает, что процесс жив
- число соединений и запросов: видно, доходит ли трафик от балансировщика
- размеры внутренних очередей: очередь есть за любым асинхронным вызовом и ест память
- версия и подключение к зависимостям

**Представляться** - каждый запрос несёт, какой сервис его послал. Без этого источник аномального потока запросов ищут долго, а это может быть забытый на ночь нагрузочный тест на прод. ([33:35](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2015))

Способы от простого к строгому: ([35:06](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2106))
- заголовок с именем вызывающего: его скопируют вместе с кодом, но часть случаев он закроет
- отдельная очередь Kafka на каждого потребителя
- zero trust: сертификат подтверждает, кто подключился, а конфиг - что ему можно

Зная вызывающего, можно ставить rate limit на конкретного потребителя ([[sre-L04-архитектура-надёжных-сервисов#Лимиты|L04]]) и отфильтровать взбесившийся сервис. ([36:30](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2190))

## Микросервисы: изоляция ценой сложности

Каждый разрез на сервисы взвешивают: какие преимущества и недостатки в нём сыграют. Почти все преимущества следуют из изоляции, поэтому где она не нужна, микросервисы не нужны. ([50:13](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3013))

| Цена границы сервиса                                         | Что даёт изоляция                               |
| ------------------------------------------------------------ | ----------------------------------------------- |
| сетевой вызов медленнее вызова в памяти                      | части релизят по отдельности                    |
| CPU на сериализацию: крупные экономят на ней тысячи серверов | нерестартуемое живёт отдельно от остального     |
| совместимость API вместо рефакторинга с проверкой типов      | фатальная ошибка или утечка роняет один сервис  |
| метрики, логи, таймауты, повторы, лимиты на каждый вызов     | лимиты CPU и памяти на сервис (cgroups, Docker) |
|                                                              | разные языки: под задачу и под найм             |

([41:39](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2499))

Микросервисы не повышают надёжность, это миф. После первого распила сбоев больше, пока среда не даст трассировку и логи, а инженеры не научатся дебажить по сети; потом надёжность можно вернуть почти к прежней. ([51:23](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3083))

**Закон Конвея** - архитектура сервисов повторяет организационную структуру: команды хотят свой сервис, а не делят систему по необходимости. ([53:23](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3203))

**Модульный монолит** - модули пишут разные команды по контрактам, но контракты - локальные интерфейсы в одном процессе. Нет сетевых вызовов и лишних задержек, но нет и изоляции ресурсов. ([55:31](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3331))
