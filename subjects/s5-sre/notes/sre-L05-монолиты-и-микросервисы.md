# L05. Монолиты, микросервисы и эксплуатация

Продолжение чеклиста из [[sre-L04-архитектура-надёжных-сервисов]]: по каждому пункту решать осознанно. ([00:21](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=21))

## Рестарт

Цель: как можно больше компонентов можно рестартовать в любой момент, не задумываясь. Тогда при сбое сначала рестартуют, а причину ищут потом. ([01:07](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=67))

- рестарт заново поднимает соединения, чистит память и кэши, применяет новый конфиг
- что рестартовать нельзя, должно быть **записано поимённо**: почему нельзя и почему решили это не чинить
	- например, БД с долгой проверкой индексов при старте или потоковое распознавание речи
- свой рестарт не должен ломать соседей лавиной переподключений (см. [[sre-L04-архитектура-надёжных-сервисов#Запуск и переподключение]])
- управляемая остановка: перестать принимать работу, завершить начатое, закрыть соединения
- рестарт иногда усугубляет сбой: баг проявлялся только при старте, и проблема с 3 нод из 100 перешла на все ([06:56](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=416))
- не оставлять на диске "конфиг на следующий рестарт": о нём забудут

## Совместимость версий

([10:15](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=615))

| Что              | Сколько держать совместимость                                   |
| ---------------- | --------------------------------------------------------------- |
| публичный API    | мобильные клиенты обновляются неохотно: "считайте, что вечно"   |
| веб-клиент       | обновлением управляете вы: пользователь загружает свежий сайт   |
| API в датацентре | по лектору, базово ~3 месяца: можно откатиться на столько назад |
| данные в БД      | на несколько версий; это нарушают чаще всего                    |

- миграция, которая удаляет или заменяет поля, делает откат невозможным или дорогим ([12:41](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=761))

**Расширение и сужение схемы** - формат данных меняют только добавлением, а старое удаляют отдельным поздним изменением. ([13:24](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=804))

1. Добавить новое поле, сохранив старое.
2. Код пишет оба варианта, читает новое, если оно есть, иначе старое.
3. Когда версии долго прожили без критичных багов, удалить старое поле, затем код его чтения.

- в Google все поля делали nullable и старые почти не удаляли; цена - сотни неиспользуемых полей ([14:19](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=859))
- откат кода не отменяет внешний эффект: проведённый платёж нужно компенсировать; иногда безопаснее исправление вперёд

## Сквозной ID

По лектору, его стоит заложить почти всегда и сразу: внедрять потом очень сложно. ([17:15](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1035))

- входящий запрос получает ID, тот передаётся в исходящие вызовы и пишется в логи (см. [[sre-P04-логи-и-метрики#Практики]])
- поиск по ID показывает логи запроса со всех сервисов: трассировка по цене логов
- по лектору, трассировка почти не отличается от логов со сквозным ID, её системы лишь лучше держат нагрузку
- ID кладут в каждое сообщение Kafka: очередь - тот же вызов, только с ожиданием ([20:54](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1254))
- **сэмплирование логов**: при огромном потоке хранить, например, 10% запросов, выбирая по ID целиком во всех сервисах ([22:11](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1331))
- флаг debug в запросе включает подробные логи только для него ([23:57](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1437))
- trace ID, correlation ID: в общем случае одно и то же; называть, как принято в компании, и не спорить ([25:58](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1558))

## Самодиагностика

Серьёзный сервис по стандартному адресу отдаёт HTML-страницу о себе, как в Google. Это быстрее, чем искать усреднённые графики в Grafana. ([29:51](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=1791))

- на ней активные соединения, размеры внутренних очередей, версия, состояние зависимостей, поток запросов
- видно, доходят ли до сервиса запросы, которые показывает балансировщик
- доступ ограничивают, секретов и содержимого запросов на странице нет

## Представляться

Сервис должен знать, кто к нему пришёл: иначе источник аномального потока ищут долго (стажёр запустил нагрузочный тест на прод). ([33:35](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2015))

- минимум: заголовок с именем вызывающего сервиса; его могут скопировать, но часть случаев он закрывает
- по нему фильтруют взбесившегося клиента и ставят **rate limit на потребителя**, а не на весь сервис
- максимум - **zero trust**: без подтверждённого сертификата и разрешения в конфиге запрос не пускают ([37:10](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2230))
	- сертификат подтверждает, кто подключился; авторизация - что ему можно

## Микросервисы vs монолит

"Никакого версуса нет": для каждого разреза взвешивают плюсы и минусы. ([40:39](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2439))

| Недостатки                                                | Преимущества                              |
| --------------------------------------------------------- | ----------------------------------------- |
| задержка: сетевой вызов медленнее вызова в памяти         | разные языки: удобство под задачу и найм  |
| CPU на сериализацию и десериализацию                      | независимые релизы по частям              |
| совместимость API вместо рефакторинга в IDE               | падение затрагивает один сервис, а не всё |
| на каждый вызов метрики, логи, таймауты, повторы, лимиты  | изоляция ресурсов: лимиты CPU и памяти    |
| повторы перемножаются: 3 уровня по 3 попытки - 27 вызовов | отдельное масштабирование                 |

- то, что нельзя рестартовать, выносят в отдельный сервис и больше ничего туда не добавляют ([48:06](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=2886))
- почти все преимущества следуют из **изоляции**: если она не нужна, не смотрите в сторону микросервисов ([50:13](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3013))
- общая БД, очередь или шлюз снова связывают сервисы

**Позиция лектора: микросервисы не повышают надёжность**, это миф. Они менее надёжны, чем монолит, и лишь большой работой их можно с ним сравнять. ([51:23](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3083))

- первый распил даёт больше сбоев, пока нет трассировки и инженеры не научились дебажить по сети
- после переписывания доступность (про прошлое) ещё высокая, а надёжность (свойство сейчас) уже другая, см. [[sre-L01-надёжность-и-доступность#Надёжность и доступность]] ([57:04](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3424))

**Закон Конвея** - архитектура сервисов повторяет организационную структуру. ([53:23](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3203))

**Модульный монолит** - модули с контрактами, которые пишут разные команды, но выпускают вместе: своя зона у команды без сетевых вызовов, но и без изоляции ресурсов. ([55:31](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3331))

Любой асинхронный вызов порождает очередь ожидающих ответа: она ест память, её ограничивают и мониторят. ([57:51](https://tbank.ktalk.ru/recordings/iKErqYAjYvycYKe9kf4C?t=3471))
