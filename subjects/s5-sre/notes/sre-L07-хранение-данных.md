# L07. Хранение данных

## Данные живут не только в базе

Данные хранят и в памяти приложения, файлах, очередях, бэкапах, на устройствах пользователей, у партнёров, в логах. Возможностей базы там нет, их изобретают или живут без них, но иногда это выгоднее. ([05:13](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=313))

| Место                    | Пример из лекции                                                     |
| ------------------------ | -------------------------------------------------------------------- |
| Память приложения        | поисковый индекс в RAM; после рестарта его надо восстанавливать      |
| Бэкапы                   | статистика по бэкапу не нагружает прод и заодно проверяет бэкап      |
| Устройства пользователей | WhatsApp хранил переписку на телефонах, сервера только маршрутизировали |
| Логи                     | на логах пишут бизнес-логику, и они становятся вашим API             |

Неизменяемые данные упрощают всё: логи только дописывают, поисковый индекс магазина можно целиком пересобирать раз в сутки. Постоянно меняющиеся остатки на складе уже требуют базы. ([10:19](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=619))

## Тип базы: гарантии против масштаба

**Модель данных** - как представлены данные и связи: таблицы, документы, графы, иерархии, векторы. Чем лучше данные ложатся на модель, тем проще приложение. ([22:28](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=1348))

Типы баз различаются тем, какие гарантии отдают за масштаб. ([25:08](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=1508))

| Тип                    | Что даёт                                        | Чем платит                                 |
| ---------------------- | ----------------------------------------------- | ------------------------------------------ |
| SQL                    | транзакции и ограничения (уникальность, ссылки) | плохо масштабируется на огромные данные    |
| NoSQL                  | огромный масштаб или скорость на частной задаче | нет ограничений или транзакций             |
| NewSQL (например, YDB) | SQL и транзакции при горизонтальном масштабе    | транзакции между узлами медленнее          |

SQL будет в любой системе, потому что транзакции слишком удобны. Для большого масштаба делают микс: важное с гарантиями в SQL, поток обращений в NoSQL. ([29:22](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=1762))

## Выбирать по операциям с данными

Базы кардинально различаются тем, что делают быстро, медленно или не умеют вовсе. Недостающее придётся делать в приложении, выкачав много данных, а это много кода и багов. Поэтому сначала решают, что нужно делать с данными. ([33:36](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=2016))

| Операция             | Разброс между базами                                     |
| -------------------- | -------------------------------------------------------- |
| Доступ по ключу      | есть почти везде; в Redis и S3 почти только он           |
| Связи по ключу       | документные почти не умеют, графовые на них построены    |
| Фильтрация           | от полного отсутствия (S3) до огромных возможностей SQL  |
| Полнотекстовый поиск | формы слов и ранжирование; в Elasticsearch, PostgreSQL   |
| Изменение            | по полю, целиком или только дописывание                  |
| Агрегация            | от ничего до оконных функций                             |

Граница атомарности тоже разная. Поменять балансы двух людей в MongoDB - "та ещё задачка": параллельные записи конфликтуют. ([44:27](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=2667))

```sql
-- SQL: условное изменение может затронуть строки разных таблиц
UPDATE products SET stock = stock - 1
WHERE id = 42 AND stock > 0;   -- 0 изменённых строк: товара не было
```

```js
// MongoDB: атомарно только в пределах одного документа; по слайду, для нескольких нужна транзакция
db.products.updateOne({ _id: 42, stock: { $gt: 0 } }, { $inc: { stock: -1 } })
```

## Индекс ускоряет одно ценой другого

Индекс организует хранение так, что быстрыми становятся только некоторые операции, а каждый лишний индекс замедляет запись. Поэтому базы и разные. ([49:33](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=2973))

| Индекс               | Устройство                                                         | Для чего                         |
| -------------------- | ------------------------------------------------------------------ | -------------------------------- |
| Хеш                  | хеш ключа указывает место на диске                                 | запись по точному ключу          |
| B-дерево             | упорядоченные ключи в узлах                                        | поиск, диапазоны, сортировка     |
| SSTable и LSM-дерево | данные копят в памяти, сортируют и пишут неизменяемым блоком; блоки сливают | огромные объёмы почти без изменений |
| Инвертированный      | для каждого слова - список документов; поиск пересекает списки     | любой полнотекстовый поиск       |

Узел B-дерева подбирают под блок, который диск читает за раз. Дерево получается неглубоким: поиск - условно 4 чтения диска. ([53:16](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=3196))

В LSM изменение пишут новой записью с пометкой, поиск берёт самую свежую, а слияние схлопывает старые версии. ([58:43](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=3523))

## Данные кладут под характер работы

Если данные лежат не под ваши запросы, база читает с диска лишнее, и всё работает медленно. ([01:08:43](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=4123))

| Хранение   | Рядом лежат                         | Удобно                                  |
| ---------- | ----------------------------------- | --------------------------------------- |
| Строчное   | все поля одной записи               | работа с записью целиком: SQL, MongoDB  |
| Колоночное | значения одного поля у всех записей | аналитика: 2-3 поля по множеству записей |

Базы оптимизируют и под профиль: под запись (изменения дороги), под чтение (каталог подложили целиком) или под холодное хранение. Холодное хранилище дёшево держит то, что почти не читают: бэкапы, большинство видео YouTube. ([01:09:49](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=4189))

**Репликация** - несколько копий одних данных: больше чтений и защита от отказа оборудования. **Шардирование** - данные кусками распределяют по серверам. ([01:15:11](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=4511))

По лектору, шардирование и партиционирование - синонимы. ([01:23:06](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=4986)) (вне конспекта) В PostgreSQL партиционирование делит таблицу на части внутри одной базы. ([документация](https://www.postgresql.org/docs/current/ddl-partitioning.html))

## ACID и BASE

**ACID** - свойства транзакций, за которые любят SQL-базы. Их полная реализация и делает базы медленными, поэтому появились NoSQL. ([01:16:51](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=4611))

| Свойство                  | По лектору                                                         |
| ------------------------- | ------------------------------------------------------------------ |
| Atomicity, атомарность    | изменения в разных строках и таблицах применяются все или ни одно  |
| Consistency, целостность  | заданные правила не нарушит никакая транзакция                     |
| Isolation, изоляция       | на максимальном уровне транзакция выглядит единственной; при конфликте её повторяют |
| Durability, долговечность | подтверждённое переживёт рестарт или отключение питания            |

- C в ACID не та, что в [[sre-L03-распределённые-системы#CAP|CAP]]: там речь о согласованности копий
- по лектору, настоящей durability нет: при ударе топором по серверу или баге подтверждённое может пропасть

**BASE** - гарантии многих NoSQL-баз, например Cassandra: в системе из тысяч серверов что-то не работает всегда. ([01:23:27](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=5007))
- Basically Available: часть узлов недоступна, а система всё равно обслуживает
- Soft state: прочитанное может поменяться
- Eventually consistent: если систему перестать трогать, состояние сойдётся

По лектору, CAP говорит о невозможности, а BASE - о конкретных гарантиях: доступность ценой soft state. ([01:29:34](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=5374))

Бывают системы даже без гарантии сходимости: в рекламе стороны никогда не сойдутся в числе показов и следят только, чтобы расхождение было небольшим. ([01:26:46](https://tbank.ktalk.ru/recordings/NpcRxKqJi1dqEI1JWki1?t=5206))
