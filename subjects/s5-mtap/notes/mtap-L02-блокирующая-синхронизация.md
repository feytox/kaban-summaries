# L02. Блокирующая синхронизация

Код восстановлен по демо лектора и мог выглядеть на экране иначе.

## Гонка

Ни ОС, ни язык не ограничивают потокам доступ к общей памяти: запретить работать всем, кроме одного потока, слишком дорого для многоядерного процессора. Поэтому доступ потоков к данным синхронизирует сам разработчик. ([03:29](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=209))

**Гонка** (race condition) - результат программы зависит от порядка, в котором потоки попадают в критическую секцию. ([04:13](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=253))

В демо два потока одновременно переводят по 100 рублей со счёта Васи, на котором 100 рублей. Оба проходят проверку баланса до списания, и у Васи оказывается -100. ([08:34](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=514))

```csharp
if (from.Balance >= amount)   // чтение и решение
{
    from.Balance -= amount;   // действие: проверка к этому моменту могла устареть
    to.Balance += amount;     // += тоже не атомарен: read, increment, write
}
```

Обе строки ломаются одинаково: поток прочитал значение, принял решение, а пока он пишет, другой поток уже изменил данные. Поэтому блокировка нужна и на отправителя, и на получателя. ([25:21](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=1521))

```csharp
lock (from)
lock (to)
{
    if (from.Balance >= amount) { from.Balance -= amount; to.Balance += amount; }
}
```

- порядок вложенных блокировок разобран в [[mtap-L03-дедлоки-и-cas#Дедлок|L03]]

Синхронизация через `Sleep` и задержки не работает, "даже не пытайтесь": `Sleep` может испортить код, но не починить. Локально и на CI тайминги совпадут, а на проде нет. ([59:20](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=3560))

## lock и Monitor

**Примитив синхронизации** - средство против гонок; основной, которым пользуются в 99% случаев, - `lock`. ([18:10](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=1090))

**Критическая секция** (эксклюзивная блокировка) - участок кода, который в один момент времени выполняет только один поток. Объект в `lock (x)` - имя этой секции: можно сказать, что заблокирован код, а можно, что объект. ([11:50](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=710))

`lock` - синтаксический сахар над `Monitor`. Поток, который не смог войти, встаёт в очередь объекта и дальше не выполняется. ([30:41](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=1841))

```csharp
bool lockTaken = false;
try
{
    Monitor.Enter(vasya, ref lockTaken);
    SendMoney(vasya, petya, 100);
}
finally
{
    if (lockTaken) Monitor.Exit(vasya);   // блокировку отпустят даже при исключении
}
```

- без `finally` исключение внутри секции оставит блокировку захваченной, и всё зависнет
- флаг `lockTaken` нужен из-за `ThreadAbortException`: устаревший `Thread.Abort` мог выбросить его в любой точке, даже до `Enter`
- `Monitor.TryEnter` не встаёт в очередь: возвращает `bool`, и поток идёт дальше

Блокировка защищает, только если в секцию заходят все потоки: поток без `lock` спокойно испортит данные, как человек, который прошёл к врачу через дыру в стене рядом с дверью. ([17:45](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=1065))

## Объект блокировки

Потоки синхронизируются, только если блокируются на одном и том же объекте, а не на одной переменной. Поэтому объект должен быть общим для потоков и неизменным: обычно это приватное поле. ([12:34](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=754))

```csharp
private static readonly object syncRoot = new();   // readonly - моё дополнение
```

| Объект                          | Что ломается                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------- |
| локальная переменная            | у каждого вызова свой объект, обогнать некому                                    |
| строка, которую потом изменили  | строка неизменяема: `Replace` создаёт новый объект, каждый блокируется на своём  |
| строковый литерал               | одинаковые литералы интернируются в один объект: несвязанные секции станут одной |
| публичное поле                  | кто-то присвоит новый объект, и потоки разойдутся по разным "дверям"             |

([47:13](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=2833)), ([50:36](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=3036)), ([54:07](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=3247))

## Mutex

**Mutex** - объект ОС с эксклюзивной блокировкой. Его находят по строковому имени, поэтому он работает между процессами, даже написанными на других языках. ([37:21](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=2241))

```csharp
var mutex = new Mutex(initiallyOwned: false, "my-app");   // true: создатель сразу владеет мьютексом
if (mutex.WaitOne(TimeSpan.FromSeconds(1)))               // false, если за секунду не дождался
{
    try { /* критическая секция */ }
    finally { mutex.ReleaseMutex(); }                     // try/finally пишешь сам
}
```

- таймаут в `WaitOne` - сколько ждать входа, а не сколько держать секцию
- мьютексов в ОС ограниченное число, как и потоков: забытый `Release` их съедает
- по лектору, освободить мьютекс может, скорее всего, только захвативший поток
	- по документации `ReleaseMutex` из чужого потока бросает `ApplicationException` (вне конспекта, [docs](https://learn.microsoft.com/en-us/dotnet/api/system.threading.mutex.releasemutex))

Лектор использовал мьютекс, чтобы на голом железе не работали два экземпляра приложения, которое пишет на диск, например при обновлении. ([41:51](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=2511))

## Semaphore

**Семафор** - многоместная критическая секция: внутрь пускают до N потоков. Он ограничивает параллелизм, а для эксклюзивной блокировки не подходит. ([01:04:35](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=3875))

```csharp
var semaphore = new Semaphore(initialCount: 2, maximumCount: 10);
semaphore.WaitOne();   // свободных мест -1; при 0 поток встаёт в очередь
semaphore.Release();   // свободных мест +1, но не больше maximumCount
```

`initialCount` - сколько мест свободно сейчас, `maximumCount` - до скольки их можно нарастить вызовами `Release`. Пример лектора: счётчик свободных мест задаёт, сколько ещё реплик запустить, а при нагрузке его поднимают `Release`. ([01:09:48](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=4188))

## ReaderWriterLock

Читатели данных не портят, и блокировать их друг от друга незачем. Но читатель не должен увидеть промежуточное состояние, когда писатель изменил данные в одном месте и ещё не изменил в другом. ([01:01:49](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=3709))

```csharp
var rw = new ReaderWriterLockSlim();
rw.EnterReadLock();  try { /* читают сколько угодно потоков */ } finally { rw.ExitReadLock(); }
rw.EnterWriteLock(); try { /* один писатель, без читателей */ } finally { rw.ExitWriteLock(); }
```

- пришедший писатель блокирует новых читателей и ждёт, пока выйдут текущие
- read lock - только договорённость: запись под ним не даст ошибки ни при компиляции, ни в рантайме
- лектор ждёт здесь ошибок от нейросети: она не видит, что код выполняется под read lock, взятым далеко выше

## Сравнение примитивов

| Примитив                 | Сколько потоков внутри         | Между процессами | Реентерабелен |
| ------------------------ | ------------------------------ | ---------------- | ------------- |
| `lock` / `Monitor`       | 1                              | нет              | да            |
| `Mutex`                  | 1                              | да               | да            |
| `Semaphore`              | N                              | да               | нет           |
| `SemaphoreSlim`          | N                              | нет              | нет           |
| `ReaderWriterLockSlim`   | много читателей или 1 писатель | -                | -             |

([01:15:39](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=4539))

**Реентерабельность** - возможность потока, который уже держит блокировку, взять её ещё раз. ([01:17:08](https://kontur.ktalk.ru/recordings/mY563QzooY8BgJaaRej3?t=4628))

- `Slim`-версии работают только внутри процесса, зато быстрее
- межпроцессность и реентерабельность `ReaderWriterLockSlim` на лекции не обсуждали
