# L09. Телеметрия: логи, метрики, дашборды

Теория перед практикой L10. Трассировки и алертинг лектор перенёс на начало L10.

## Сигналы и наблюдаемость

**Телеметрия** - сигналы, которые приложение отправляет наружу о своей работе; стандарт OpenTelemetry описывает три. Каждый отвечает на свой вопрос. ([09:48](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=588))

| Сигнал      | На какой вопрос отвечает                                                 |
| ----------- | ------------------------------------------------------------------------ |
| Метрики     | насколько хорошо работает система в целом, но не почему                  |
| Логи        | почему приложение сделало то или иное                                    |
| Трассировки | какой путь прошёл запрос: какие сервисы и БД, тайминги, ретраи, ошибки   |
| Исключения  | в каком релизе появилась ошибка и сколько пользователей её видят (Sentry) |

**Мониторинг** - алерты и дежурства, почти всегда по метрикам. Алерт обычно приходит, когда часть пользователей уже видит ошибку. ([13:46](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=826))

**Наблюдаемость (observability)** - свойство системы: насколько просто понять причину проблемы. Чем больше полезных логов и метрик, тем это проще. ([16:56](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=1016))

## Логи пишут так, чтобы по ним искать

Когда серверов несколько, агент собирает логи в общее хранилище, чтобы искать в одном месте. Файл на диске остаётся нормой для системных сервисов и СУБД: при аварии сети он сохранится. ([19:04](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=1144))

В текстовом логе события записаны в разных форматах, а стектрейс разрывает событие на строки, поэтому точный фильтр составить трудно. В структурированном логе (JSON, protobuf) видны границы события и именованные поля. ([25:13](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=1513))

```json
{"ts": "2026-11-13T10:00:01Z", "level": "error",
 "template": "Upstream {upstream} refused connection",
 "upstream": "10.0.0.5:8080",
 "trace_id": "4bf92f3577b34da6"}
```

Пример мой. Trace ID запроса пишут в лог отдельным полем: по трейсу находят сервис, где всё пошло не так, а по trace ID в его логах - почему. ([28:07](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=1687))

**Шаблон сообщения (message template)** - уникальная строка или код на каждый тип события. По нему находят все события одного типа с одинаковым набором полей и безопасно строят по ним фильтры. ([30:04](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=1804))

## Loki индексирует только метки

Elasticsearch задуман как поисковик и индексирует весь текст, поэтому тяжёлый; Grafana Loki - лёгкая альтернатива. ([40:05](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=2405))

|                 | Elasticsearch                       | Grafana Loki                          |
| --------------- | ----------------------------------- | ------------------------------------- |
| Индекс          | весь текст, с морфологией           | только метки и время                  |
| Поиск по тексту | быстрый                             | медленнее                             |
| Ресурсы         | ресурсоёмкий                        | лёгкий, масштабируется горизонтально  |

## Метрики и перцентили

**Метрика** - число, которое характеризует состояние системы в момент времени. **Временной ряд (time series)** - значения метрики с одним набором меток (labels), упорядоченные по времени: линия на графике. ([44:14](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=2654))

| Тип       | Значение                           | Примеры                        | Как смотрят                 |
| --------- | ---------------------------------- | ------------------------------ | --------------------------- |
| Counter   | только растёт или сбрасывается в 0 | аптайм, число запросов         | `rate()`: запросы в секунду |
| Gauge     | любое                              | свободная память, загрузка CPU | как есть                    |
| Histogram | распределение по бакетам           | длительность запросов          | перцентили                  |

([46:20](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=2780))

```text
http_request_duration_seconds_bucket{le="0.1"}   10    # запросов не дольше 0.1 с (le - less or equal)
http_request_duration_seconds_bucket{le="+Inf"}  100   # все запросы
http_request_duration_seconds_count              100   # число наблюдений
http_request_duration_seconds_sum                42.7  # сумма длительностей
```

Числа мои. По лектору, запрос увеличивает счётчик одного бакета. По документации бакеты накопительные: каждый считает все наблюдения не больше своей границы (вне конспекта, [Prometheus](https://prometheus.io/docs/concepts/metric_types/#histogram)). ([48:41](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=2921))

Гистограмма позволяет считать перцентили, а без неё доступно только среднее, которое сдвигает один выброс. При 99 значениях по 1 и одном 100 среднее около 2, а медиана и p95 ровно 1. ([50:56](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3056))

Смотрят медиану, p95 и p99, но не p100: это максимум, а несколько аномальных запросов будут всегда. ([52:48](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3168))

## Кардинальность

**Кардинальность** - число уникальных комбинаций меток метрики, то есть число её временных рядов. ([56:48](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3408))

```text
http_requests_total{method, status_code}            # ~7 методов x ~30 кодов = ~210 рядов
http_requests_total{method, status_code, user_id}   # x 1 млн пользователей = ~210 млн рядов
```

Метки с уникальными значениями (user ID, request ID) - антипаттерн: TSDB (база временных рядов) тратит на них много памяти и тормозит, а 210 млн линий не прочитать и не поставить на алерт. Конкретного пользователя ищут в трейсах и логах. ([59:12](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3552))

## Доставка: push, pull, коллекторы

| Модель | Как                                                     | Пример                           |
| ------ | ------------------------------------------------------- | -------------------------------- |
| Push   | приложение само шлёт метрики в хранилище                | Graphite, Prometheus Pushgateway |
| Pull   | приложение отдаёт метрики на `/metrics`, агент забирает | Prometheus                       |

([01:01:17](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3677))

Prometheus находит цели через service discovery, например поды Kubernetes с нужными аннотациями. Короткая cron-задача не доживёт до опроса, поэтому пушит в Pushgateway, а Prometheus опрашивает его. ([01:02:55](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3775))

**Коллектор** - промежуточный агент (Grafana Alloy, OTel Collector): принимает метрики по разным протоколам, добавляет метки о том, где запущено приложение, и шлёт в хранилище. Так сервисы на разных языках пишут как удобно. ([01:06:12](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=3972))

**OpenTelemetry** - набор стандартов, что и как отправлять, независимый от бэкенда. Приложение пишет через OTel SDK, а бэкенд выбирают настройкой SDK или коллектора. ([01:30:25](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=5425))

## Что собирать

Трафик, ошибки и задержки говорят, работает ли система быстро и без ошибок, насыщенность - сколько ещё работы она примет. По насыщенности сразу видно, кончились ли ресурсы или причину ошибок искать в приложении. ([01:10:37](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=4237))

| Золотой сигнал            | Что показывает                                  |
| ------------------------- | ----------------------------------------------- |
| Трафик                    | сколько обработано запросов, заказов, писем     |
| Ошибки                    | число или доля неуспешных                       |
| Задержки (latency)        | как быстро обрабатываются запросы               |
| Насыщенность (saturation) | насколько близки лимиты, например пул коннектов |

- **RED** (rate, errors, duration) - те же сигналы без насыщенности, для прикладных сервисов.
- **USE** (utilization, saturation, errors) - для инфраструктуры под сервисом.

Ещё полезны бизнес-метрики в штуках (ноль заказов - признак поломки) и время походов в зависимости: рост задержки сразу объясняется медленным сервисом. ([01:16:02](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=4562))

## Дашборд читают другие

Дашборд смотрят соседние команды, поэтому он должен читаться без усилий: легенда и единицы обязательны, ведь RPS и RPM отличаются в 60 раз. ([01:21:56](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=4916))

**Аннотация** - отметка на графике, например с версией релиза. Аномалию после [[devops-L06-service-пробы-ingress|rolling update]] сразу связывают с релизом и решают, ждать или откатывать. ([01:25:21](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=5121))

Дашборд в Grafana - JSON с запросами к источникам данных, его хранят в Git: так его восстановят при переезде и откатят случайную правку. ([01:27:37](https://fiit.ktalk.ru/recordings/qIgB75ggomT5jkOsTwyN?t=5257))
