## CI, CD и CD

| Практика               | Что даёт                                                                     |
| ---------------------- | ---------------------------------------------------------------------------- |
| Continuous integration | коммит -> сборка -> инспекции и тесты -> версия, обратная связь на каждом шаге |
| Continuous delivery    | артефакт, из которого можно развернуть приложение где угодно; затем релиз     |
| Continuous deployment  | релиз сам уходит на прод без участия человека                                |

([04:48](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=288))
- **релиз** - запись, что артефакт с таким-то идентификатором готов к проду: пакеты с зафиксированными версиями, в идеале changelog ([19:31](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1171))
- **continuous deployment** требует шлюза (quality gate), который почти гарантирует, что релиз можно катить ([20:21](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1221))
	- встречается редко и стоит дорого: кроме проверки приложения нужна дисциплина эксплуатации
	- в Контуре так катят мобильные приложения и сайты без банковских гарантий

## Этапы CI

([07:37](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=457))

- **воркеры одинаковые** для всей команды: `docker build` без платформы на ARM-маке даст образ, который не запустится на x86-64 ([14:23](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=863))

## Окружения и предсказуемость

Главная задача CI/CD - предсказуемость: на проде ровно то, что прошло тесты. ([37:33](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2253))
- окружения теста и прода готовит одна автоматика: руками даже по чеклисту они разъедутся ([23:50](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1430))
- **регрессионные нагрузочные тесты** сравнивают RPS с прошлым релизом на том же хосте; в Kubernetes для этого занимают помеченную лейблом ноду ([29:31](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1771))
- **сборка не на ноутбуке**: локальный пакет подхватил из системы другую версию библиотеки и упал на проде; в Контуре дистрибутив метят, что он собран в CI ([31:12](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1872))
- **один дистрибутив** из общего хранилища уходит и на тест, и на прод
- описание окружения (Dockerfile, ресурсы, манифесты) хранится в VCS
- **координаты дистрибутива** - репозиторий, ветка и коммит сборки (label образа, файл в zip); автоматика сверяет их на проде, в том числе против атак на цепочку поставок ([38:21](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2301))
- **каждый разработчик - эксплуататор**: писать пайплайн с нуля не обязан, понимать его и жизнь приложения в Kubernetes должен ([35:25](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2125))

## Исходный код и артефакты

**Исходный код** - изменяемое содержимое системы контроля версий. **Артефакт** - неизменяемый, часто бинарный архив, который точно идентифицируется хеш-суммой или подписью. ([40:25](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2425))
- обмен пакетами только через единый репозиторий артефактов; образу tar-архивом от коллеги не доверяют
- единая точка сборки и хранения нужна для безопасности: там работают Trivy, Hadolint

## Git

([43:58](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2638))
- **Git децентрализован** (писался под обмен патчами по почте); GitLab и GitHub централизуют его ради удобного ревью
- **SVN** централизован: удобен для монорепозитория, но упал сервер - не работает никто
- **тег** указывает на один коммит, например релизный; ветка - на последний
- при merge в master коммиты сохраняют или сжимают в один (squash) - решает команда ([50:53](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3053))
- **rebase** во многих командах запрещён: ломает историю у тех, кто работает со старой копией; лектор не понимает, зачем ребейзить ради чистоты

| Схема       | Ветки                                                  | Для кого                                     |
| ----------- | ------------------------------------------------------ | -------------------------------------------- |
| Git Flow    | master (всегда готов к проду), develop, feature, hotfix, release | 100+ разработчиков, отдельные тестировщики |
| GitHub Flow | master и короткие ветки                                | проект до ~10 человек                        |
| Trunk-based | один trunk, в SVN каждый в своей папке                 | в Git - если с репозиторием работает один    |

## Helm

**Helm** - шаблонизатор объектов для деплоя в Kubernetes, который следит за деплоем и умеет откатить конфигурацию. ([01:00:53](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3653)) Связка с пробами - в [[devops-L06-service-пробы-ingress#Helm|L06]].
- **чарт**: `Chart.yaml` (версия чарта и приложения), `templates/`, `values.yaml` с дефолтами; хранится архивом на любом HTTP-сервере
- **история релизов** лежит в Secret в namespace релиза ([01:04:27](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3867))
- версию приложения генерирует CI по SemVer, версия чарта меняется только с процессом деплоя ([01:22:06](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4926))

```yaml
# templates/deployment.yaml (фрагмент)
metadata:
  name: {{ .Release.Name }}            # имя из helm upgrade
  labels:
    app: {{ .Values.appLabel | quote }}
spec:
  replicas: {{ .Values.replicaCount }}
  ...
          resources:
            {{- toYaml .Values.resources | nindent 12 }}  # секция с отступом 12 пробелов
```

```bash
# upgrade --install - и установка, и обновление; голый install упадёт, если релиз есть
# -f перекрывает values.yaml чарта, --set перекрывает всё (в CI не используют: настройки версионируют)
# --wait: ждать Ready всех подов; не дождался за timeout - exit 1, CI падает
helm upgrade --install probes-demo ./charts/probes-app -n homework2 \
  -f values.yaml --set replicaCount=1 --wait --timeout 5m
helm history probes-demo -n homework2
helm rollback probes-demo 1 -n homework2   # откат - новая ревизия
```

([01:09:55](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4195))
- по лектору, при неудачном деплое Helm сам откатывает на прошлый успешный релиз, а без успешных релизов зависает ([01:18:07](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4687))
	- по документации автооткат включает флаг `--rollback-on-failure` (Helm 4) ([docs](https://helm.sh/docs/helm/helm_upgrade/)) (вне конспекта)
- откат возвращает всё из снимка релиза: реплики, ConfigMap и прочее
- **werf** от Флант - обёртка над Helm, выводит при деплое события кластера и логи
