# L07. CI/CD, Git, стратегии деплоя, Helm

Лекция-беседа о том, из чего состоит CI/CD и чего он добивается, плюс демо Helm. Код чарта восстановлен по трансляции.

## CI, delivery и deployment - три ступени автоматизации

**Непрерывная интеграция (CI)** - фиксация изменений, сборка, инспекции и тесты, подготовка версии и доставка, с обратной связью на каждом шаге. ([04:48](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=288))

**Continuous delivery** - ответ на вопрос, готов ли релиз к деплою: из артефакта можно поднять приложение, и тесты на нём прошли. ([06:37](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=397), [18:48](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1128))

**Continuous deployment** - путь от коммита до пользователя без участия человека: релиз катится на прод сам, если его пропустил автоматический шлюз. Это редкий и дорогой подход, потому что автор шлюза отвечает за то, что прод не сломается. ([20:21](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1221))

- Выкладку на тестовые стенды автоматизировать сравнительно дёшево, гарантию работы на проде - дорого.
- **Инспекции** - проверка соответствия кода стилю команды; синтаксис и так проверит сборка. ([08:15](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=495))
- Быстрые unit-тесты сейчас гоняет ИИ-агент до коммита, в CI важнее нагрузочные и интеграционные. ([11:18](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=678))
- **Динамический стенд** - неймспейс в Kubernetes на ветку, который живёт только на время тестов. ([16:59](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1019))

## Предсказуемость поставки

Главная задача CI/CD - предсказуемость: на проде ровно то, что прошло тесты. Окружения теста и прода готовит одна автоматика: руками даже по чеклисту они разъедутся, как сервер со старым .NET, который включили после раскатки. ([37:33](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2253), [23:50](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1430))

Дистрибутив собирают только в CI на одинаковых воркерах и из общего хранилища отдают и на тест, и на прод: пакет с ноутбука может подхватить из системы другую версию библиотеки. ([31:12](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=1872))

- `docker build` без платформы на Mac с ARM даёт образ, который не запустится на x86_64 в кластере. ([14:23](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=863))
- Описание окружения (Dockerfile, манифесты) хранят в Git, поэтому каждый разработчик - эксплуататор: понимает пайплайн, но не обязан писать его с нуля. ([35:02](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2102))

**Координаты дистрибутива** - репозиторий, ветка и коммит сборки в label образа или в файле архива. По ним автоматика проверяет, что на проде то, что тестировали, и что дистрибутив не подменили; лектор не вспомнил её название [?]. ([38:21](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2301))

| Исходный код             | Артефакт                                        |
| ------------------------ | ----------------------------------------------- |
| изменяемый, обычно текст | неизменяемый, часто бинарный архив              |
| хранится в VCS           | хранится в репозитории артефактов (registry)    |
| версия - коммит          | опознаётся по хеш-сумме или подписи             |

Пакетами обмениваются только через единый репозиторий: tar с образом от коллеги не принимают. Только так артефакты можно проверить сканерами безопасности. ([41:23](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2483))

## Git и схемы ветвления

Git задуман распределённым: копия нужного репозитория всегда есть у кого-то из разработчиков. GitLab и GitHub централизуют его ради удобного ревью, а централизованный SVN без сервера встаёт целиком. ([44:32](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=2672))

- При мерже команда либо сохраняет все коммиты ветки, либо делает squash в один большой. ([50:53](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3053))
- Rebase во многих командах запрещён: он переписывает историю, и у тех, кто брал старую копию, пропадают изменения. ([51:39](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3099))

| Схема       | Ветки                                                         | Когда                                          |
| ----------- | ------------------------------------------------------------- | ---------------------------------------------- |
| Git flow    | master - всегда релиз; develop, feature, release, hotfix      | крупные команды от 100 человек с тестировщиками |
| GitHub flow | короткие ветки прямо от master                                | проекты примерно до 10 человек                 |
| Trunk-based | все коммитят в одну ветку trunk, каждый в своей директории    | SVN-монолиты                                    |

- Для небольшого проекта лектор назвал и GitHub flow, и "обычный Git flow" [?]. ([54:37](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3277))
- По лектору, trunk-based на Git значит, что с репозиторием работает один человек. По trunkbaseddevelopment.com в trunk коммитят многие разработчики, допускаются короткие ветки для ревью (вне конспекта, [Trunk Based Development](https://trunkbaseddevelopment.com/)).

## Blue-green и canary упираются в базу данных

**Blue-green** - два стенда с разными версиями; новую проверяют, затем балансировщик переключает на неё всех пользователей. **Canary** - новую версию получает сначала одна реплика или доля трафика, и если она выживает, обновляют остальное. ([56:04](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3364))

Canary, по лектору, самая надёжная, но самая дорогая в эксплуатации: она тем точнее, чем больше телеметрии отдаёт приложение. Средствами Kubernetes её честно не сделать, см. [[devops-L06-service-пробы-ingress#Стратегия деплоя опирается на пробы]]. ([56:50](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3410))

В обеих схемах пользователи ходят в две версии сразу, поэтому миграции БД не должны ломать работу старой версии. Релиз, который переименовывает таблицы, откатывается только восстановлением базы из бэкапа. ([58:46](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3526))

## Helm - инструмент деплоя, а не только шаблонизатор

Helm шаблонизирует манифесты, следит за деплоем и откатывает конфигурацию к прошлой. Так процесс деплоя тоже описан кодом. ([1:00:53](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3653))

Чарт - это `Chart.yaml` с версией чарта и приложения, папка `templates/` и `values.yaml` со значениями по умолчанию. Обычно его упаковывают в архив и раздают по HTTP. ([1:03:34](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3814), [1:06:14](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3974))

```yaml
# templates/deployment.yaml (фрагмент)
metadata:
  name: {{ .Release.Name }}            # имя релиза из команды helm
  namespace: {{ .Release.Namespace }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    metadata:
      labels:
        app: {{ .Values.appLabel | quote }}
    spec:
      containers:
        - name: app
          resources:
            {{- toYaml .Values.resources | nindent 12 }}   # секция целиком с отступом 12
```

```bash
# install при первом запуске, upgrade при следующих; голый install упадёт, если релиз есть
# -f перекрывает values.yaml чарта, --set перекрывает и его (так не делают: значения храним в Git)
# --wait ждёт Ready всех подов, по --timeout выходит с кодом 1, и CI падает
helm upgrade --install probes-demo ./charts/probes-app -n <ns> \
  -f values.yaml --set replicaCount=1 --wait --timeout 5m
helm list -n <ns>                       # релизы и номер ревизии
helm history probes-demo -n <ns>        # ревизии: install, upgrade, rollback
helm rollback probes-demo 1 -n <ns>     # откат - новая ревизия с конфигурацией ревизии 1
```

- Историю ревизий Helm хранит в Secret в неймспейсе релиза. ([1:01:53](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=3713), [1:21:13](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4873))
- Версию приложения CI генерирует по semver, версию чарта меняют, только когда меняется процесс деплоя. ([1:22:06](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4926))
- По лектору, при неудачном деплое Helm сам откатывается на прошлый успешный, а без единого успешного зависает. По документации `helm upgrade` откатывает только с флагом `--rollback-on-failure`, в Helm 3 `--atomic` (вне конспекта, [helm upgrade](https://helm.sh/docs/helm/helm_upgrade/)). ([1:18:07](https://fiit.ktalk.ru/recordings/7Nty0Rsp2R27Jn3Cay5Q?t=4687))
