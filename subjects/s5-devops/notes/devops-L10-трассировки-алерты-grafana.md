# L10. Трассировки, алерты, практика с Grafana

Продолжение [[devops-L09-телеметрия-логи-метрики|L09]]: остаток теории и демо стека телеметрии в Kubernetes.

## Трассировка показывает, где сломался запрос

**Трассировка (trace)** - путь одного запроса через все компоненты системы. Метрики показывают систему в совокупности, а трассировка - конкретный запрос. ([02:48](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=168))

**Спан (span)** - работа одного компонента над запросом: тайминг, успех, атрибуты, свой ID. Компонент получает trace ID запроса, в HTTP почти всегда через заголовок, и помечает им свои спаны. ([03:36](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=216))

Трассировка - верхнеуровневый агрегирующий лог: по ней видно, какой сервис не ответил, где были ретраи или долгий поход в БД, не читая логи всех компонентов. Логи потом читают только у виноватого сервиса. ([05:31](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=331))

Трассировки ищут по атрибутам спанов, например все запросы, которые ходили в БД дольше секунды. Найденную показывают деревом спанов со смещениями от начала запроса. ([08:27](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=507))

```text
{ duration > 100ms }   # TraceQL в Grafana Tempo: спаны дольше 100 мс (демо)
{ status = error }     # спаны с ошибкой (пример мой)
```

- Хранилища трассировок: Grafana Tempo, Jaeger, Zipkin, Sentry.
- Чужую трассировку читать трудно, свою - просто: атрибуты спанов задаёт автор сервиса.

## Правила хороших алертов

Алерт - формула над метриками с порогом: система мониторинга периодически её вычисляет и при нарушении шлёт уведомление в канал. В Prometheus правила вычисляет сам сервер, а рассылает уведомления Alertmanager. ([11:40](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=700))

| Правило                           | Зачем                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------- |
| Перцентили, не среднее            | по среднему не понять, больше страдающих пользователей или нет                   |
| Исключать ночное время            | при малом числе запросов даже перцентили дают неадекватные значения              |
| Временное окно (`for`)            | на разовый всплеск реагировать не нужно; формула проще, чем со средним за период |
| Повторные уведомления             | в пачке алертов при большой аварии легко пропустить тот, что ещё красный         |
| Подавление и группировка          | при недоступном хосте не слать алерты по его CPU: видна корневая проблема        |
| Alerts as Code                    | ревью, массовые правки, откат, переезд на другую систему мониторинга             |
| Пересмотры                        | метрики меняются, алерты по заброшенным функциям становятся шумными              |
| Пришёл алерт - уже что-то сломано | даже если пользователи не заметили благодаря ретраям и репликам                  |

([16:07](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=967))

Лучший алерт предупреждает до поломки: место на диске или память убывают почти линейно, и можно прислать предупреждение "через 2 дня кончится место". ([25:06](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=1506))

- Системы алертинга: Alertmanager (Prometheus), Moira (Контур, open source), Grafana.

## Стек: коллектор раскладывает сигналы по хранилищам

В демо стек ставят [[devops-L06-service-пробы-ingress|Helm]]-чартами в неймспейс `monitoring`: каждому сигналу своё хранилище, а приложение знает только адрес коллектора. ([27:26](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=1646))

```text
приложение (OTel SDK) --OTLP--> Alloy   :4317 gRPC, :4318 HTTP
Alloy: метрики -> Prometheus :80, логи -> Loki :3100, трассировки -> Tempo
kube-state-metrics: состояние объектов Kubernetes (поды, фазы, рестарты) в виде метрик
Grafana: источники данных Prometheus :80, Loki :3100, Tempo :3200
```

Схема по файлам стенда. **Grafana Alloy** - коллектор, совместимый с OTel Collector. Источники данных в Grafana заданы прямо в values чарта и ссылаются на сервисы по короткому DNS-имени в том же неймспейсе. ([43:26](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=2606))

- Данные лежат в `emptyDir` без томов: рестарт пода стирает телеметрию, для учёбы это допустимо.

## Запрос к метрике зависит от её типа

Запрос PromQL - имя метрики и фильтры по меткам в фигурных скобках; функцию выбирают по [[devops-L09-телеметрия-логи-метрики#Метрики и перцентили|типу метрики]]. ([46:03](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=2763))

```promql
# gauge: рисуют как есть
process_resident_memory_bytes{job="grafana"}

# counter (rate в RED): rate даёт скорость в секунду при любом окне [1m] или [5m]
sum by (handler, status_code) (rate(grafana_http_request_duration_seconds_count{job="grafana"}[5m]))

# histogram (duration в RED): скорость по бакетам, сумма с сохранением le, затем перцентиль
histogram_quantile(0.95, sum by (le) (rate(grafana_http_request_duration_seconds_bucket{job="grafana"}[5m])))
```

Запросы из дашборда стенда. В демо p95 был 40 мс при медиане 4 мс: запросы и клиенты разные, и среднее такой разброс не показало бы. ([57:33](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=3453))

На большом диапазоне Grafana сводит несколько точек в одну, поэтому тренд смотрят на длинном интервале, а конкретные значения - на коротком. ([50:07](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=3007))

## LogQL: сначала метки, потом разбор

Loki быстро фильтрует только по индексированным меткам, а тело записи для него просто строка, даже если это JSON. Поля из тела становятся доступны после парсера в пайплайне, и всё после селектора уже не индексировано. ([01:03:23](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=3803))

```logql
{namespace="monitoring", container="grafana"}                        # селектор по меткам: индекс
{namespace="monitoring", container="grafana"} | json | level="warn"  # разбор JSON и фильтр по полю
sum(rate({namespace="monitoring", container="grafana"} | json | level="warn" [1m]))       # число предупреждений во времени
```

Поэтому алерты и графики с разбором и фильтрами по телу работают медленнее, чем привычный поиск в Elasticsearch. ([01:07:47](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=4067))

- Кроме `json` есть парсер `logfmt` для записей вида `a=b x=10`.

## Grafana связывает логи и трассировки

Из записи лога с trace ID Grafana открывает трассировку в Tempo, а из трассировки - логи нужного сервиса за время запроса. Так от ошибки в логе доходят до сервиса, который её вызвал. ([01:10:54](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=4254))

```yaml
# источник Loki в values Grafana: поле traceID из лога ведёт в Tempo
derivedFields:
  - name: TraceID
    matcherRegex: '"traceID"\s*:\s*"([0-9a-fA-F]{32})"'
    datasourceUid: tempo
```

Фрагмент из файлов стенда. Обратный переход фильтрует логи по сервису из атрибутов спана, но читать их всё равно глазами. ([01:24:25](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=5065))

## Панель не должна обманывать

У панели задают единицы: байты Grafana сама покажет как мегабайты и гигабайты. Ось Y по умолчанию подстраивается под данные, и колебание в пределах погрешности выглядит резким скачком; soft min 0 возвращает почти прямую линию. ([01:20:00](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=4800))

Дашборд как код обычно правят в интерфейсе, экспортируют в JSON и кладут в репозиторий. ([36:25](https://fiit.ktalk.ru/recordings/Lo8PuwJiLW7Jm40ylWQt?t=2185))
