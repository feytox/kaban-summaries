# L02. Docker: образы, слои, контейнеры

Docker решает проблему "у меня работает, у тебя нет": приложение едет вместе со своими библиотеками и зависимостями. Ядро ОС и железо при этом остаются хостовыми, так что окружение воспроизводится не полностью. ([05:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=327))

## Контейнер и виртуальная машина

Контейнер - обычный процесс хостовой ОС, урезанный в правах, а VM несёт свою ОС поверх гипервизора. Поэтому контейнеры дешевле, но изолированы слабее. ([08:45](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=525))

|           | VM                            | Контейнер                           |
| --------- | ----------------------------- | ----------------------------------- |
| Ядро      | своё, через гипервизор        | общее с хостом                      |
| Накладные | гигабайты RAM на ОС каждой VM | почти нет                           |
| Изоляция  | сильная                       | уязвимость ядра открывает весь хост |

- Изоляцию дают механизмы ядра Linux: namespaces (что процесс видит) и cgroups (сколько ресурсов берёт). ([07:07](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=427))
- Внутри контейнера процесс приложения получает PID 1. ([13:31](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=811))
- На практике VM и контейнеры совмещают: контейнеры запускают внутри VM, а VM делят приложения по требованиям безопасности. ([12:09](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=729))

## Dockerfile, образ, контейнер

Docker - это клиент (CLI), который по API шлёт команды серверу (демону), а сервер собирает образы и запускает контейнеры, локально или на удалённой машине. Третья часть - registry, хранилище образов, по аналогии с GitHub для репозиториев. ([14:19](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=859))

**Dockerfile** - текстовый файл, декларативно описывающий итоговое состояние образа. ([18:43](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1123))

**Образ (image)** - собранный артефакт, из которого запускаются контейнеры; его пушат в registry и пулят обратно.

**Контейнер** - запущенный образ; из одного образа можно запустить сколько угодно контейнеров. ([19:35](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1175))

```bash
docker build -t myapp:1.0 .          # "." - контекст сборки, Dockerfile ищется в его корне
docker run -d --name web -p 8080:5000 myapp:1.0   # в фоне, порт хоста 8080 -> 5000 контейнера
docker ps -a                         # все контейнеры, включая завершившиеся
```

- Любой Dockerfile начинается с `FROM`: базового образа ОС или языка, который кто-то уже собрал и выложил в Docker Hub. ([20:37](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1237))
- Без тега подставляется `latest`, и следующая сборка его перезатрёт: зависимость от `latest` делает систему невоспроизводимой. ([29:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1753))
- Docker - лишь одна из реализаций стандарта образов (OCI), поэтому собранный локально образ запускается и в Kubernetes. ([1:29:06](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5346))

## Слои и кэш сборки

**Слой** - неизменяемый снимок изменений файловой системы после инструкции Dockerfile, как дифф коммита в Git. Образ - стопка слоёв, и одинаковый слой хранится один раз: в registry компании образ Python лежит в одном экземпляре на все сервисы. ([34:29](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2069))

При сборке Docker сверяет хэш каждого шага с кэшем и переиспользует слой, пока всё выше не изменилось. `COPY` и `ADD` сравнивают содержимое файлов, а `RUN` - только текст команды, поэтому `apt-get update` не перевыполнится от выхода новых пакетов. ([47:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2847))

Первое изменение инвалидирует все слои ниже, отсюда главное правило Docker: чем чаще меняется слой, тем ниже он в Dockerfile. ([49:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2953))

```dockerfile
FROM python:3.14-slim
WORKDIR /app
COPY requirements.txt .               # меняется редко
RUN pip install -r requirements.txt   # тяжёлый шаг остаётся в кэше
COPY . .                              # код меняется часто - копируем последним
USER app
CMD ["python", "app.py"]
```

Отдельный `COPY requirements.txt` - не костыль: без него любое изменение кода переустанавливает зависимости. ([52:34](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3154))

## Размер образа

Слой нельзя уменьшить задним числом: файл, удалённый следующей инструкцией, остаётся в образе, как файл в истории Git. Поэтому мусор чистят в том же `RUN`, где он появился. ([1:00:34](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3634))

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends nginx \
    && rm -rf /var/lib/apt/lists/*    # кэш apt не попадёт в слой
```

- Лишние слои тоже вредны: по лектору, их не больше 255, считая слои базового образа. ([57:53](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3473))
	- предел 127 слоёв (`MaxImageDepth` в коде Docker) ([Docker Forums](https://forums.docker.com/t/how-to-flatten-an-image-with-127-parents/1600)) (вне конспекта)
- **Multi-stage сборка** - несколько стадий `FROM` в одном Dockerfile: компилятор и кэши остаются в стадии сборки, в итоговый образ копируется только результат; так собирают C# и Go. ([1:04:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3853))
- `.dockerignore` не пускает в контекст `.git`, `.venv`, env-файлы и тестовые артефакты. ([1:06:44](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4004))

## Данные контейнера

Контейнер эфемерен: его изменения живут в тонком слое записи поверх образа и исчезают при удалении контейнера. Гарантированы только файлы, попавшие в образ при сборке. ([1:08:03](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4083))

| Способ     | Где хранится                            | Зачем                                         |
| ---------- | --------------------------------------- | --------------------------------------------- |
| volume     | область на хосте под управлением Docker | штатный способ сохранять данные               |
| bind mount | директория хоста, видна 1 в 1           | локальная разработка: код без пересборки      |
| tmpfs      | оперативная память                      | секреты, которые должны умереть с контейнером |

([1:20:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4827))
- Новые слои появляются только от инструкций Dockerfile при сборке, работающий контейнер их не создаёт. ([1:32:35](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5555))
- Завершившийся контейнер висит, пока его не удалят, как зомби-процесс ([[mtap-L01-потоки-и-процессы]]); флаг `--rm` удаляет его сразу. ([1:16:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4587))

## Безопасность

Контейнеры делят ядро, поэтому о безопасности думают при написании Dockerfile. ([27:26](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1646))
- Без `USER` процесс работает от root, и взломанному приложению проще добраться до ядра.
- Сеть контейнера закрыта, порты наружу пробрасывают явно.
- Секреты не пишут в Dockerfile: они видны в образе. ([1:29:06](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5346))
