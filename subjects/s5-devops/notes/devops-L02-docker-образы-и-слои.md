# L02. Docker: образы, слои, хранение данных

## Контейнеры и виртуальные машины

Docker решает проблему "у меня работает, у тебя нет": приложение переносят вместе с библиотеками и окружением. Ядро ОС и железо (процессор, его инструкции) при этом остаются разными, полной воспроизводимости нет. ([06:05](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=365))

- **по лектору**, Docker - это настроенные namespaces и cgroups Linux; механизмы появились в 2008, Docker лишь упаковал их в удобный инструмент ([07:07](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=427))
- контейнер для ОС - обычный процесс с урезанными правами: видит только разрешённые файлы, ограничен по CPU и памяти, внутри у него PID 1

|          | Виртуальная машина                    | Контейнер                                     |
| -------- | ------------------------------------- | --------------------------------------------- |
| ОС       | своя на каждую, гигабайты RAM впустую | общее ядро хоста                              |
| Изоляция | полная, через гипервизор              | неполная: уязвимость ядра открывает весь хост |

([08:45](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=525))
- на практике их совмещают: контейнеры запускают внутри VM, а по VM разносят приложения по требованиям безопасности, чтобы уменьшить радиус поражения ([12:09](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=729))

## Устройство Docker

([14:19](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=859))
- **клиент** - CLI, шлёт команды серверу по API; сервер может быть и удалённым
- **сервер** (демон) собирает образы и запускает контейнеры
- **registry** - хранилище образов, "GitHub для образов": публичный Docker Hub или корпоративный

**Образ (image)** - собранный по Dockerfile артефакт, который пушат в registry и из которого запускают контейнеры. ([18:43](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1123))

**Контейнер** - запущенный образ; из одного образа можно запустить сколько угодно контейнеров.

```bash
docker build -t myapp:1.0 .            # . - контекст сборки
docker build -f other.Dockerfile .     # Dockerfile может лежать где угодно и называться как угодно
docker build --platform linux/amd64 .  # сборка на ARM (Mac) для x86-серверов
docker run -d --name app -p 8080:8080 myapp:1.0  # -d - в фоне, порты наружу только явно
docker run --rm myapp:1.0              # удалить контейнер после завершения
docker ps -a                           # включая завершённые
```

- **CMD и ENTRYPOINT** по лектору: CMD передаёт аргументы списком, ENTRYPOINT вызывает `/bin/sh -c` ([23:33](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1413))
	- (вне конспекта) по документации ENTRYPOINT задаёт исполняемую команду, CMD - аргументы по умолчанию, которые заменяются аргументами `docker run`; через `/bin/sh -c` идёт shell-форма любой из них, exec-форма (JSON-список) запускается напрямую ([docs](https://docs.docker.com/reference/dockerfile/#entrypoint))
- **тег** не указан - будет `latest`; лектор считает это антипаттерном: новый `latest` перезапишет старый, и сборка перестанет воспроизводиться ([29:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1753))
- по умолчанию контейнер работает от **root**: при взломе приложения так проще добраться до ядра, поэтому создают пользователя через `USER` ([27:26](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=1646))
- секреты не кладут в Dockerfile: они будут видны в образе ([01:29:06](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5346))
- Docker - лишь реализация стандарта OCI-образов: образ, собранный локально, развернётся в Kubernetes как под ([[sre-P02-основы-kubernetes|SRE P02]]); есть и другие сборщики (Kaniko и др.)

## Слои и кэш

**Слой** - снапшот изменений файловой системы после инструкции, по сути diff, как коммит в Git; размер слоя в `docker history` - размер этого diff. ([34:29](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2069))

- слои неизменяемы: файл, удалённый в следующем слое, всё равно весит в образе, как удалённое видео в истории Git ([01:37:17](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5837))
- слой переиспользуется, если совпал хэш всей цепочки до него; одно изменение пересобирает все слои ниже ([40:35](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2435))
- одинаковые базовые слои хранятся в registry один раз: у компании с единым Python лежит одна копия базового образа и разные слои кода
- что проверяется для кэша ([47:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2847))
	- `COPY`, `ADD` - хэши файлов: даже пустая строка пересоберёт слой
	- `RUN` - только текст команды: `apt update` не пересоберётся, когда выйдут новые пакеты
- слой контейнера: при запуске поверх образа появляется тонкий записываемый слой, новые слои образа создаёт только сборка ([01:32:35](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=5555))
- число слоёв ограничено, по лектору около 255, включая слои базового образа ([57:53](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3473))
	- (вне конспекта) исторический предел - 127 слоёв, дальше ошибка `max depth exceeded` ([moby/buildkit#4815](https://github.com/moby/buildkit/pull/4815))

## Хороший Dockerfile

**Главное правило:** чем чаще меняется слой, тем ниже он в Dockerfile. Зависимости копируют и ставят до кода, иначе каждая правка кода переустанавливает их (минуты в CI). ([49:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=2953))

```dockerfile
FROM python:3.14-slim          # тег конкретный, не latest
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/* \
    && useradd app             # установка и чистка в одном слое
WORKDIR /app
COPY requirements.txt .        # сначала только файл зависимостей (uv: pyproject.toml + uv.lock)
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                       # код меняется чаще всего - последним
USER app
CMD ["python", "app.py"]
```

Пример мой, собран по правилам с пары.

- **одна инструкция `RUN`** на установку и чистку: отдельный `RUN rm` не уменьшит образ, а лишний слой занимает место и время ([59:59](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3599))
- **multi-stage**: компилятор и кэш сборки остаются в первой стадии, в итоговый образ копируют только бинарник; для C# и Go это стандарт ([01:04:13](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=3853))
- **`.dockerignore`**: не класть в контекст `.git`, `.venv`, env-файлы, тестовые артефакты ([01:06:44](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4004))

## Данные контейнера

Контейнер эфемерный: всё, что он записал у себя, пропадает при его удалении; гарантированы только файлы из образа. ([01:18:23](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4703))

- завершённый контейнер висит, пока его не удалят: аналогия с зомби-процессом, чей exit code никто не прочитал; помогает `--rm` ([01:14:14](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4454))

| Способ     | Где данные                             | Для чего                                 |
| ---------- | -------------------------------------- | ---------------------------------------- |
| volume     | объект под управлением Docker на хосте | штатный способ, рекомендуемый            |
| bind mount | директория хоста 1 в 1                 | локальная разработка: код без пересборки |
| tmpfs      | оперативная память                     | секреты, исчезают вместе с контейнером   |

([01:20:27](https://fiit.ktalk.ru/recordings/3tOKUcCu31PuH6ao2fmU?t=4827))
