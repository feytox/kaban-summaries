# L04. Системы хостинга

Лектор - Дмитрий Рубцов, вводная лекция к блоку про Kubernetes. Устройство Kubernetes подробнее в [[sre-P02-основы-kubernetes|SRE P02]].

## Что такое хостинг

**Хостинг** - передать код на вычислительные мощности, открыть его пользователям, наблюдать за ним и управлять им: перезапускать, конфигурировать. ([02:46](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=166))

- **изоляция** (контейнеризация) защищает систему от приложения, а приложение - от атак снаружи
- **репликация** нужна для отказоустойчивости и горизонтального масштабирования
- **кластер** - набор изолированных процессов разного назначения: несколько бэкендов, фронтендов

## Контейнеры

- виртуализация и контейнеризация развивались параллельно, а не одна после другой ([11:53](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=713))
- итог - контейнеры на виртуалках: VM режут большой сервер и запускают чужую архитектуру, контейнеры изолируют на уровне ядра (ср. [[devops-L02-docker-образы-и-слои#Контейнеры и виртуальные машины|L02]]) ([14:43](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=883))
- **Windows-контейнеры** работают только на той же сборке Windows, что хост: обновился хост - пересобирай все образы; в Контуре их не используют, 99% контейнеров на Linux ([17:40](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1060))

Изоляция контейнеров не стопроцентная, это скорее обещание хостинга, чем гарантия. ([19:09](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1149))
- cgroups ограничивают долю процессорного времени, а не ядра; throttling включается не сразу, и жадный процесс успевает помешать соседям
- в ядре Linux регулярно находят уязвимости, через которые процесс видит чужие namespaces

**Контейнер** - механизм запуска приложения с изоляцией по namespaces и системным ресурсам; Docker - лишь пользовательский интерфейс к нему ("руль и педали", а containerd - "шасси и двигатель"). ([28:42](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1722))

| Уровень        | Инструменты                | Что умеет                                               |
| -------------- | -------------------------- | ------------------------------------------------------- |
| клиенты        | Docker, Podman             | сборка, push в registry, запуск, сеть, тома             |
| низкоуровневые | LXC/LXD, containerd, CRI-O | без человеческого интерфейса объясняют ядру, что делать |

([25:14](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1514))
- в большинстве кластеров Kubernetes Docker нет, поэтому `docker build` там не выполнить; сборка образа - задача ноутбука или CI-раннера ([27:49](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1669))
- образ для CI - артефакт: исходники -> образ -> registry -> контейнер

## Оркестраторы

[[devops-L03-dive-хранение-compose#Docker Compose|Docker Compose]] - самая базовая система хостинга в пределах одной ОС: стенд разработчика, БД в контейнере. Если сервер упал, кто-то (человек или Ansible) должен запустить `docker compose up` на другой ноде. Это автоматизирует оркестратор. ([31:33](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1893))

## Kubernetes

Как в Ansible, описываешь желаемое состояние. Но Ansible отработал и завершился, а Kubernetes постоянно сверяет кластер с описанием и чинит расхождения. ([41:53](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2513))

Компоненты - в таблице [[sre-P02-основы-kubernetes#Архитектура|SRE P02]]. Добавки лектора: ([44:16](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2656))
- пользователь ходит в API server через `kubectl`
- kubelet работает не с ядром, а с containerd, CRI-O или Docker; ещё он настраивает iptables для трафика между подами
- worker (kubelet) один на ноду, а не на контейнер

Чего Kubernetes **не делает**: ([48:48](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2928))
- не деплоит: для этого есть Helm и другие инструменты
- не мониторит и не отвечает за корректность: "работает" значит "процесс ещё не вышел с ненулевым кодом"
- логи и диагностику настраиваешь сам

**Pod** - минимальная единица: своя подсеть и IP, контейнеры внутри общаются через localhost, могут делить том и всегда живут на одной ноде. ([54:58](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3298))
- в под объединяют неразделимое: бэкенд и следящий за ним агент метрик (sidecar); в общем случае под = один контейнер ([57:12](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3432))
- **реплика и под - одно и то же**: 3 реплики приложения = 3 пода ([01:18:51](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4731))

Новый под проходит `Pending` (kubelet тянет образ из registry) и становится `Ready`, как только процесс запустился и не упал. Работает ли приложение на самом деле, проверяют пробы, обычно запросом на `/status`. ([01:08:24](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4104))

По лектору, если контейнер в поде завершился с любым кодом, перезапускается весь под; сам Kubernetes отдельный контейнер не трогает. По документации kubelet перезапускает упавшие контейнеры пода по `restartPolicy`, сам под при этом остаётся ([docs](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#container-restarts)) (вне конспекта). ([01:11:12](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4272))
- под `Running`, а счётчик рестартов растёт: например, Java или .NET не влезают в heap, и OOM killer перезапускает контейнер по кругу ([01:13:10](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4390))
- на это ставят триггер: больше 10 рестартов за 10 минут - приложение, скорее всего, не работает

Реплики нужны для отказоустойчивости (хватит двух) и масштабирования. ([01:19:13](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4753))

**HPA** (Horizontal Pod Autoscaler) - добавляет реплики, когда под использует больше заданной доли лимита CPU (например, 70%), в границах min/max, и убирает лишние при спаде; метрики CPU поставляют сервисы, которые ставят админы кластера.

Kubernetes не управляет виртуалками: ноды готовят другие инструменты (в Контуре - Ansible-роли), в managed-кластере облака - автоматика облака. Для проверки "как моё приложение работает в Kubernetes" есть minikube, kind и k3s, но они не масштабируются на много серверов. ([01:02:42](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3762))
