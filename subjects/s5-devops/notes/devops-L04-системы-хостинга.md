# L04. Системы хостинга: контейнеры, оркестраторы, Kubernetes

**Хостинг** - передать код на вычислительные мощности, пустить к нему пользователей, видеть, что происходит внутри, и управлять им: перезапускать, конфигурировать. ([02:46](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=166))

## Виртуализация и контейнеризация

Виртуализация и контейнеризация развивались параллельно и решают разные задачи ([[devops-L02-docker-образы-и-слои#Контейнер и виртуальная машина]]), поэтому их совмещают: на сервере крутятся ВМ, а в ВМ - контейнеры. ([11:53](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=713))

|              | Виртуальная машина                            | Контейнер                                    |
| ------------ | --------------------------------------------- | -------------------------------------------- |
| Ядро         | своё; гипервизор транслирует вызовы в хостовое | общее с хостом                               |
| ОС и арх.    | может отличаться от хоста                     | та же ОС и архитектура, что у хоста          |
| Накладные    | прослойка гипервизора                         | прослойки нет, железо утилизируется лучше    |
| Зачем нужна  | запустить код другой архитектуры, нарезать большой сервер | изоляция на уровне ядра               |

([12:45](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=765), [14:43](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=883))


## Изоляция контейнеров - обещание, а не гарантия

Контейнер - обычный процесс, которого ядро ограничивает по видимости (namespaces) и по ресурсам (cgroups). Оба механизма не дают 100% изоляции, поэтому лектор называет её обещанием хостинга. ([19:09](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1149))

- cgroups ограничивают не ядра, а долю процессорного времени: виртуального ядра у контейнера нет.
- Троттлинг включается не мгновенно, и "злой" процесс успевает задеть соседей.
- В ядре периодически находят уязвимости, через которые процесс видит чужие namespaces. ([22:07](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1327))

## Контейнер - не только Docker

**Контейнер** - механизм запуска приложения с изоляцией на уровне ядра по namespaces и по системным ресурсам. Docker лишь пользовательский интерфейс к нему: руль и педали, а шасси с двигателем - низкоуровневый рантайм. ([28:42](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1722))

| Уровень  | Примеры                    | Что делает                                                             |
| -------- | -------------------------- | ---------------------------------------------------------------------- |
| Клиент   | Docker, Podman             | собирает образ, пушит в registry, поднимает контейнер, сеть, тома      |
| Рантайм  | containerd, CRI-O, LXC/LXD | объясняет ядру, как поднять и изолировать процесс, настроить iptables  |

([25:14](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1514))

- Образ - артефакт: его собирают, кладут в registry и из него поднимают контейнер на хостинге. ([23:24](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1404))
- На нодах Kubernetes Docker обычно нет: хостинг только запускает контейнеры, а сборка образа - задача ноутбука или CI-раннера. ([27:49](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1669))

## Оркестратор нужен, когда хостов больше одного

Docker Compose описывает приложение в пределах одной ОС ([[devops-L03-dive-хранение-compose#Docker Compose]]). Для отказоустойчивости реплики живут на разных хостах, и при отказе одного копию на другом поднимает **оркестратор**, а не инженер вручную. ([31:33](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=1893))

- Docker Swarm - "пикап": построен на Docker-клиенте, кластер на пачке ВМ можно поднять за вечер.
- Kubernetes, Nomad, Mesos, OpenShift - "самосвалы"; Kubernetes - стандарт для продакшена. ([38:47](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2327))
- Kubernetes - не готовый хостинг, а платформа: компании строят свой хостинг через расширение API.
	- **CRD** (Custom Resource Definition) - свой тип объекта Kubernetes со своим обработчиком. ([39:37](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2377))
- Swarm уместнее, где нет команды под Kubernetes: в Контуре это больше 5 человек. ([37:54](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2274))

## Kubernetes держит желаемое состояние

В Kubernetes декларативно описывают, что хотят видеть на проде, например 3 реплики. В отличие от Ansible, который отработал плейбук и завершился, Kubernetes постоянно сверяет кластер с желаемым состоянием и чинит расхождение. ([42:42](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2562))

| Часть         | Компонент          | Роль                                                        |
| ------------- | ------------------ | ----------------------------------------------------------- |
| Control plane | kube-apiserver     | HTTP-API, с которым работает `kubectl`                      |
|               | etcd               | хранилище желаемого состояния                               |
|               | scheduler          | выбирает ноду для запуска                                   |
|               | controller manager | следит, что в кластере всё соответствует описанию           |
| Worker        | kubelet            | запускает поды через рантайм, настраивает iptables на ноде  |
|               | kube-proxy         | связывает поды на разных нодах                              |

([44:16](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2656))

- Worker - один на ноду, а не на контейнер. ([50:01](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3001))
- Kubernetes не деплоит (для этого Helm), не мониторит и не отвечает за корректность: под для него жив, пока процесс не вышел с ненулевым кодом. ([48:48](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=2928))

Манифест состоит из секций `apiVersion`, `kind`, `metadata`, `spec`, вложенность задаётся двумя пробелами. Код восстановлен по слайду. ([51:09](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3069))

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3            # желаемое состояние: 3 пода
  template:
    spec:
      containers:        # ресурсы и образ - уже на уровне пода
        - name: web
          image: registry.example.com/web:1.0
```

## Под - единица запуска

**Под** - минимальная единица хостинга в Kubernetes: группа неотделимых друг от друга контейнеров со своим IP. Контейнеры пода всегда на одной ноде, общаются через localhost и могут делить том, как на одной ВМ. ([54:58](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3298))

- **Sidecar** - вспомогательный контейнер в поде, например экспортёр метрик рядом с Postgres. ([57:12](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3432))
- Реплика - это под: 3 реплики приложения из nginx и бэкенда дают 3 пода и 6 контейнеров. ([1:00:04](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3604))
- **ReplicaSet** - объект, который держит нужное число подов; если ноду некуда заменить, он пытается бесконечно. ([1:00:50](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=3650))

Новый под проходит Pending (kubelet тянет образ из registry) и Ready. По умолчанию Ready значит лишь "процесс запустился и не вышел", поэтому о реальной работе приложения Kubernetes узнаёт из проб (liveness, readiness), например запроса на `/status`. ([1:08:24](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4104))

По лектору, при падении любого контейнера перезапускается весь под, а отдельный контейнер (например, после OOM) перезапускается сам, без участия Kubernetes. ([1:10:19](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4219)) По документации, упавший контейнер перезапускает kubelet по `restartPolicy` пода, а под целиком заменяют, только если его не восстановить (вне конспекта, [Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-fault-recovery)).

Под в Running с растущим счётчиком рестартов, скорее всего, не работает: на это ставят алерт. ([1:13:10](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4390))

## Реплики и canary

Реплики нужны для отказоустойчивости (хватает двух) и для масштабирования под нагрузку. ([1:19:13](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4753))

**HPA** (Horizontal Pod Autoscaler) - добавляет реплики, когда под съедает больше порога CPU (например, 70% лимита), и убирает лишние при спаде, в заданных границах. ([1:20:10](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4810))

**Canary-релиз** - обновить часть реплик и по ним решить, идти ли дальше. Нужно решить, сколько реплик обновлять за раз (из 1000 одна получит слишком мало запросов) и как понять, что реплика работает: локальные health check'и или отдельный health check API. ([1:21:27](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=4887))

- Rolling update лектор считает одной из реализаций canary.
- Не прошла проверка: Helm откатывает реплики к прошлым конфигам и секретам. Service тем временем не пускает запросы на сломанную реплику. ([1:23:40](https://fiit.ktalk.ru/recordings/o6nhS2Und73uVOzFVEaC?t=5020))
